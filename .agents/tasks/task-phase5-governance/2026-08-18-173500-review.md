# Governance layer: policy engine, secret vault, audit chain, and operational safety subsystems

This change adds a comprehensive governance layer to NEXUS: a deterministic policy engine with deny-first evaluation, an encrypted secret vault with versioning, a hash-chained audit logger, multi-level rate limiting, tenant isolation enforcement, and supporting subsystems (rollback, incidents, retention, health, config governance). Three new API route modules and a governance middleware tie the surface together. Watch for: secrets stored as plaintext in the database via the API routes despite the domain-level vault providing encryption (confirmed); the `/api/v1/policies/evaluate` endpoint implements its own evaluation logic that diverges from the `PolicyEngine` class (confirmed); tenant guard's `check_resource_ownership` fails-open for unregistered resources (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The policy engine properly implements deny > budget_cap > rate_limit > require_approval > allow precedence with default-deny, and the v1 fix correctly makes `rate_limit` signal intent without denying. However, the `/api/v1/policies/evaluate` endpoint re-implements evaluation logic from scratch using a `rules.get("effect")` / `rules.get("actions")` schema that has no relationship to the `PolicyEngine`'s `PolicyRule.rule_type` and condition-matching system — meaning the API test-evaluation will produce different results from actual engine evaluation.

The secrets API routes store `body.value` and `body.new_value` directly into the database `encrypted_value` column without calling any encryption function. The comments say "In production, encrypt before storing" but nothing guards against shipping this code path. The domain-level `SecretVault` properly encrypts via `_TestOnlyXOREncryptor`/`_FernetEncryptor`, but the API layer bypasses it entirely.

The tenant guard raises `TenantViolation` exceptions for registered cross-tenant access but returns `True` for unregistered resources, creating a fail-open posture where any resource not explicitly registered is accessible to all tenants. The `_scan_for_foreign_tenants` method performs unbounded recursion on response data with no depth limit.

<details>
<summary>Issues (4)</summary>

1. **Secrets API stores plaintext in `encrypted_value` column** — The `create_secret` and `rotate_secret` route handlers write `body.value` / `body.new_value` directly to the database without encrypting. Either integrate the `SecretVault` encryptor at the route level or add an encryption step before DB writes.
2. **Policy evaluate endpoint diverges from PolicyEngine** — `/api/v1/policies/evaluate` checks `rules.get("effect")` and `rules.get("actions")` instead of using `PolicyEngine.evaluate()`. The API endpoint's evaluation logic will produce different allow/deny decisions than the actual engine. Wire the endpoint to instantiate a `PolicyEngine` with the DB policies or at minimum use the same schema.
3. **Tenant guard fails-open for unregistered resources** — `check_resource_ownership` returns `True` when a resource is not in the registry. In a multi-tenant system, any resource created before tenant guard initialization or through a code path that doesn't register is silently accessible to all tenants. Default should be deny or require explicit registration.
4. **Unbounded recursion in `_scan_for_foreign_tenants`** — The recursive scan of response data has no depth limit. A deeply nested payload (e.g., from a recursive data structure or adversarial input) will hit Python's default 1000-frame recursion limit and crash with `RecursionError`.

## Secrets API bypasses encryption entirely

The `create_secret` route handler stores the raw value:

```python
secret = Secret(
    company_id=company_id,
    name=body.name,
    category=body.category,
    encrypted_value=body.value,  # In production, encrypt before storing
    current_version=1,
    expires_at=body.expires_at,
)
```

Similarly, `rotate_secret` writes `body.new_value` directly:

```python
.values(
    current_version=new_version_number,
    encrypted_value=body.new_value,  # In production, encrypt
    ...
)
```

The `SecretVersion` records also store the raw value. The column is named `encrypted_value` but contains plaintext. A database dump exposes every secret. The domain-level `SecretVault` class handles encryption correctly — the API routes just never call it.

## Policy evaluation endpoint uses incompatible schema

The `/api/v1/policies/evaluate` endpoint at `src/nexus/api/routes/policies.py` implements its own evaluation:

```python
for policy in policies:
    if policy.rules:
        applicable_actions = policy.rules.get("actions", [])
        if applicable_actions and body.action in applicable_actions:
            matching_policies.append(...)
            if policy.rules.get("effect") == "deny":
                allowed = False
```

The domain-level `PolicyEngine` uses `PolicyRule` objects with `rule_type` (deny/allow/require_approval/rate_limit/budget_cap) and a `conditions` dict with keys like `actor_type`, `action`, `resource_type`, `time_hour_min`, etc. The API endpoint expects `rules.actions` (a list) and `rules.effect` (a string) — a completely different schema. A policy created via the API and one loaded into the `PolicyEngine` from builtins will evaluate differently depending on which path processes the request.

## Tenant guard fail-open for unregistered resources

In `check_resource_ownership`:

```python
owner = self._resource_registry.get(key)
if owner is None:
    # Resource not registered - allow (it may be new)
    return True
```

The guard only provides protection for resources explicitly registered via `register_resource()`. Any resource accessed through a code path that skips registration — or any resource that existed before the guard was initialized — is implicitly accessible to every tenant. For a system claiming "hard tenant isolation enforcement" (the module docstring), the correct default for a security boundary is deny-when-unknown.

## Unbounded recursion in tenant data scanning

`_scan_for_foreign_tenants` recurses into every dict value and list item:

```python
if isinstance(data, dict):
    for value in data.values():
        foreign.extend(self._scan_for_foreign_tenants(company_id, value))
elif isinstance(data, list):
    for item in data:
        foreign.extend(self._scan_for_foreign_tenants(company_id, item))
```

No depth limit is applied. A response containing a circular reference (possible if the serializer doesn't prevent it) or a deeply nested legitimate structure will produce a `RecursionError`. Adding a `max_depth` parameter with a reasonable default (e.g., 10) would prevent crashes without limiting the utility of the scan.
