# Governance layer: policy engine, secret vault, audit chain, and operational safety subsystems

This change adds a comprehensive governance layer to NEXUS: a deterministic policy engine with deny-first evaluation, an encrypted secret vault with versioning, a hash-chained audit logger, multi-level rate limiting, tenant isolation enforcement, and supporting subsystems (rollback, incidents, retention, health, config governance). Three new API route modules and a governance middleware tie the surface together. The v2 review's four blocking issues (plaintext secrets in DB, divergent policy evaluation, tenant guard fail-open, unbounded recursion) are all resolved. Watch for: the Fernet encryptor in the secrets route generates a new random key on every process restart, making previously encrypted secrets unrecoverable (confirmed); the governance middleware stubs out policy evaluation, rate limiting, budget checking, and audit logging behind permissive defaults with TODO comments (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The secrets API now encrypts values before database writes, but the Fernet path instantiates `_FernetEncryptor()` with no key argument, meaning each process start generates a fresh random key. Secrets encrypted in a previous process lifetime become undecryptable. The XOR fallback uses a hardcoded key that is stable across restarts but provides no real confidentiality. Neither path is production-viable without externalized key management.

The governance middleware is registered on the FastAPI app and correctly enforces the kill switch, but its `_evaluate_policy`, `_get_rate_limit_remaining`, `_estimate_request_cost`, `_check_budget`, and `_audit_log_request` methods all return permissive defaults with TODO markers. In practice, the middleware provides only kill-switch protection and audit-to-stdout for mutating requests — none of the other governance subsystems are wired in at the request level.

The subsystems exist in-domain but are not connected to the request path. Either wire them in or document the middleware as enforcement-incomplete so downstream consumers know the request-level governance checks are no-ops.
3. **Hardcoded XOR fallback key in secrets route** — When `cryptography` is unavailable, `_ENCRYPTION_KEY = b"route-level-secret-encryption-key"` is used for XOR obfuscation. This is static, committed to source, and provides no confidentiality. Acceptable for local testing but the TODO should be promoted to a startup guard that refuses to boot in production without a proper key.

## Secrets route key management gap

The secrets route module initializes encryption at import time:

```python
_ENCRYPTION_KEY = b"route-level-secret-encryption-key"

if _HAS_FERNET:
    _encryptor = _FernetEncryptor()  # generates random key internally
else:
    _encryptor = _TestOnlyXOREncryptor(_ENCRYPTION_KEY)
```

When the `cryptography` library is available, `_FernetEncryptor.__init__` calls `Fernet.generate_key()` — a fresh 32-byte random key each time. After a process restart, the new key cannot decrypt values stored under the old key. The column `encrypted_value` accumulates ciphertext that becomes permanently orphaned.

The fix: accept a key from an environment variable or app settings, and pass it to `_FernetEncryptor(key=...)`. The TODO comment on line 19-20 acknowledges this but doesn't guard against the dangerous default.

## Middleware enforcement gap

The `GovernanceMiddleware` actively checks the kill switch via `_KillSwitchRegistry`. Every other governance function returns a permissive stub:

```python
def _evaluate_policy(self, request, company_id):
    # TODO: Wire to PolicyEngine.evaluate(context) for real policy enforcement
    return {"allowed": True}

def _check_budget(self, company_id, estimated_cost):
    # TODO: Wire to BudgetEnforcer.check(company_id, estimated_cost)
    return True
```

The `PolicyEngine`, `RateLimiter`, `PersistentAuditLogger`, and `BudgetEnforcer` exist as in-memory domain objects but no request ever consults them. Consumers inspecting the middleware registration in `main.py` might assume full enforcement is active when only the kill switch actually gates requests.

## v2 fixes verified

All four v2 issues are resolved: secrets API encrypts via `_encryptor.encrypt()` before DB write; policy evaluate endpoint uses `PolicyEngine` with proper rule/context conversion; `check_resource_ownership` returns `False` for unregistered resources; `_scan_for_foreign_tenants` has `max_depth=10`.
