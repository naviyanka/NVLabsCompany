# Governance layer: policy engine, secret vault, audit chain, and operational safety subsystems

This change adds a full governance layer to NEXUS: a deterministic policy engine (deny > require_approval > allow), an XOR-based secret vault with rotation and revocation, a persistent audit logger with SHA-256 hash chain for tamper detection, a compliance framework with data classification, a token-bucket rate limiter with sliding window, a tenant guard with hard isolation, a rollback manager with cascading undo, an incident manager with auto-detection, a data retention manager with legal holds, a health monitor with circuit breaking, configuration governance with approval workflow, and API middleware plus three new route modules (policies, secrets, incidents) backed by new SQLModel tables. Watch for: the XOR "encryption" in the vault provides zero confidentiality guarantees if the key leaks or is predictable (confirmed); the governance middleware integration points are all stubs that unconditionally pass, meaning the middleware currently does nothing in production (confirmed); the rate limiter and all domain managers are purely in-memory with no persistence, so a process restart loses all state (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The policy engine implements deny > budget_cap > rate_limit > require_approval > allow evaluation with default-deny. However the `rate_limit` rule type unconditionally denies the request rather than deferring to the actual rate limiter, meaning any agent subject to `rate_limit_per_agent` will be denied on every evaluation regardless of actual request volume.

The secret vault stores values encrypted with XOR-against-key when the `cryptography` library is unavailable (the production constraint in this INTEGRATIONS_ONLY sandbox). XOR with a repeating key is trivially reversible — it's a shift cipher. The vault design (versioning, binding, revocation, access logging) is sound, but the encryption primitive undermines the security claim.

The persistent audit logger's SHA-256 hash chain has no persistence across restarts — `_last_hash` resets to `"genesis"` on every instantiation, breaking integrity verification across process boundaries.

All governance domain managers (rate limiter, tenant guard, rollback, retention, health, config governance, incidents) are in-memory dataclass stores, but the API routes for policies, secrets, and incidents use SQLAlchemy/SQLModel against a real database — creating an architectural split where the API layer is persistent but the domain logic layer is not. Nothing connects the database `Policy` model to the `PolicyEngine` evaluation logic.

The governance middleware registers on every request but every check method is a hard-coded stub returning the permissive default. Enforcement is currently zero.

<summary>Issues (7)</summary>

1. **XOR encryption provides no confidentiality** — Replace `_Base64Encryptor` with an actual symmetric cipher (e.g., AES-CTR via stdlib or bundled pure-Python implementation), or clearly mark the vault as test-only and gate production use on `_HAS_FERNET`.
2. **rate_limit rule type unconditionally denies** — The policy engine returns `allowed=False` for any matched `rate_limit` rule without consulting actual request counts. Either remove `rate_limit` from policy evaluation or integrate with the RateLimiter to check actual token state.
3. **Governance middleware is entirely stubbed** — All enforcement methods return permissive defaults. Wire them to the actual domain managers (PolicyEngine, TenantGuard, RateLimiter, PersistentAuditLogger) or remove the middleware until integration is ready, to avoid false confidence.
4. **In-memory state lost on restart** — RateLimiter, TenantGuard, RollbackManager, IncidentManager, HealthMonitor, ConfigGovernance, and RetentionManager all store state in Python dicts/lists with no serialization. Document this limitation or add persistence hooks.
5. **Audit hash chain not resumable** — PersistentAuditLogger starts from `"genesis"` on every instantiation. If the process restarts, new entries won't chain from the last persisted hash, breaking integrity verification across restarts.
6. **No tests for API routes or middleware** — The seven test files cover domain logic only. The three new route modules and the middleware have zero test coverage.
7. **Nighttime policy time logic off-by-one** — `nighttime_restricted` sets `time_hour_min=17, time_hour_max=8`, intending to match outside business hours. The engine's wrapped-range logic (`hour >= min_hour or hour <= max_hour`) matches hours 17–23 and 0–8 — but the policy description says "9-17" while the condition fires at hour 17 (5 PM) itself, triggering during the last hour of business rather than after it.

## XOR encryption in the secret vault

When `cryptography` is not importable (the case in this sandbox), `SecretVault` falls back to `_Base64Encryptor`:

```python
class _Base64Encryptor:
    def encrypt(self, plaintext: str) -> bytes:
        data = plaintext.encode("utf-8")
        key_bytes = self._key
        encrypted = bytes(
            b ^ key_bytes[i % len(key_bytes)] for i, b in enumerate(data)
        )
        return base64.urlsafe_b64encode(encrypted)
```

This is a repeating-key XOR cipher. Given the ciphertext and knowledge of the key length (or a known-plaintext fragment), recovering the key is trivial. In a multi-tenant system storing API keys and tokens, a database dump or memory inspection exposes all secret values with negligible effort.

The `encryption_key` parameter defaults to `os.urandom(32)` if not provided, and there's no mechanism to persist or rotate the vault key itself — meaning every process restart generates a new key, making all previously "encrypted" values unrecoverable.

## Policy engine rate_limit rule short-circuits evaluation

In `PolicyEngine.evaluate()`, matched `rate_limit` rules are handled after deny and budget_cap but before `require_approval`:

```python
if rate_limit_matches:
    policy, rule = rate_limit_matches[0]
    return PolicyDecision(
        allowed=False,
        decision_type="rate_limit",
        policy_name=policy.name,
        reason=f"Rate limited by policy: {policy.name}",
    )
```

The `rate_limit_per_agent` built-in policy matches any request where `actor_type == "agent"`. The condition check only verifies the actor type, not actual rate. Every agent request that enters policy evaluation will be denied with "rate limited" regardless of actual throughput. The domain-level `RateLimiter` class (token bucket + sliding window) is never consulted by the policy engine.

## Middleware stub architecture

`GovernanceMiddleware` is added to the FastAPI app in `main.py` and dispatches on every request:

1. `_is_company_killed(company_id)` → always returns `False`
2. `_get_rate_limit_remaining(company_id)` → always returns `DEFAULT_RATE_LIMIT` (100)
3. `_evaluate_policy(request, company_id)` → always returns `{"allowed": True}`
4. `_estimate_request_cost(request)` → always returns `0`
5. `_check_budget(company_id, cost)` → always returns `True`
6. `_audit_log_request(...)` → logs to Python `logging.info` only

None of the newly-created domain managers are instantiated or referenced by the middleware. The rate limit headers injected into responses are cosmetic constants. The audit log goes to stdout, not to `PersistentAuditLogger`.

## API routes vs domain managers: two parallel universes

The three new API routes (`/api/v1/policies`, `/api/v1/secrets`, `/api/v1/incidents`) operate directly against SQLModel/SQLAlchemy with full CRUD, versioning, and tenant scoping via `CurrentCompanyId`. But the domain-layer classes (`PolicyEngine`, `SecretVault`, `IncidentManager`) are standalone in-memory objects with no database backing. An API user can create a policy via the REST endpoint, but the `GovernanceMiddleware` will never evaluate it because the middleware doesn't read from the database.

## Tenant isolation: fail-open for unknown resources

`TenantGuard.check_resource_ownership` returns `True` for unregistered resources ("it may be new"), which means any resource not explicitly registered is implicitly accessible to all tenants — fail-open by default. Additionally, `_scan_for_foreign_tenants` performs unbounded recursion on arbitrarily nested dicts/lists; a deeply nested response could hit Python's recursion limit.

## Rate limiter check-then-consume race

The `consume()` method calls `check_rate_limit()` first (which peeks via `bucket.check()`), then calls `bucket.consume()` separately. Between the check and the consume, `_refill` is called twice (once in `check`, once in `consume`), slightly inflating available tokens under rapid sequential calls. In a single-threaded async context this is marginal, but it means the limiter is not strictly accurate at boundary conditions.

## Hash chain not resumable across restarts

`PersistentAuditLogger` initializes `_last_hash = "genesis"` unconditionally. After a restart, new entries begin a fresh chain disconnected from prior entries. `verify_chain_integrity` will only validate entries from the current process lifetime, providing no protection against tampering with previously persisted (if ever persisted) entries.

## Test coverage gaps

Not tested: `GovernanceMiddleware` (no integration tests), API routes for policies/secrets/incidents (no endpoint tests), `PersistentAuditLogger` (no dedicated test file), `RetentionManager` (no dedicated test file), `HealthMonitor` (no dedicated test file), `ConfigGovernance` (no dedicated test file). The middleware and route layer — the only production-facing surface — has zero coverage.
