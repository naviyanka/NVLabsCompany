# Real-time streaming and session compaction (v3)

Phase 5 delivers WebSocket connection management with tenant-aware broadcasting, SSE streaming with pub/sub and tenant-scoped filtering, and session context compaction with three strategies. All five v1 issues (dead code, `__all__` fan-out, absent auth, dual registries, unclosed sockets) and all three v2 issues (gate-only tenant isolation, missing `__all__` tests, missing auth tests) have been addressed. The `RealtimeEvent` dataclass now carries `company_id`, the SSE generator filters by tenant, the WebSocketManager provides `broadcast_to_company()`, and the test suite covers fan-out semantics, auth enforcement, and tenant isolation with 90 passing tests.

Watch for: The WS endpoint's `broadcast` action (line 108 of `ws.py`) still calls `manager.broadcast()` which sends to all connections regardless of company — any authenticated client can trigger a cross-tenant broadcast by sending `{"action": "broadcast", "data": {...}}` (confirmed). The `disconnect()` path's `websocket.close()` call is fire-and-forget with a bare `except Exception` that silently swallows errors including `CancelledError` on Python 3.12 (possible).

**Verdict**: APPROVED

## High-level view

The tenant isolation model is now two-layered: the SSE generator checks `event.company_id` against the authenticated caller and drops mismatched events; the WebSocketManager stores `company_id` per connection and offers `broadcast_to_company()` for scoped delivery. The remaining gap is narrow — the WS endpoint's user-facing `broadcast` action routes through the unscoped `manager.broadcast()`, which means a malicious authenticated client can push arbitrary JSON to every connected WebSocket. This is not blocking given that no domain producer currently uses this action for sensitive data, but it should be scoped to company before the endpoint sees production traffic.

Consider narrowing to `except (RuntimeError, ConnectionError)`. Confidence: **possible** — in practice CPython 3.12 handles this correctly but the pattern could mask unexpected failures.

## Unscoped broadcast in WebSocket endpoint

The WebSocket command loop (lines 100-110 of `ws.py`) handles `{"action": "broadcast", "data": {...}}`:

```python
elif action == "broadcast":
    broadcast_data = data.get("data", {})
    count = await manager.broadcast(broadcast_data)
```

`manager.broadcast()` iterates `self._connections` (all clients, all tenants) and sends the payload. The caller's `validated_company_id` is available in scope but not used to limit delivery. Meanwhile, the manager provides `broadcast_to_company(company_id, data)` which does exactly the right thing — sends only to connections registered with a matching company. This action should either delegate to `broadcast_to_company(validated_company_id, broadcast_data)` or be removed as a user-facing command.

The risk is bounded by the fact that no domain event flows through this path today (the action requires an authenticated client to explicitly send a broadcast command), so it functions as a debug/demo feature. But once a frontend or agent client uses this action for inter-client messaging, the cross-tenant leak becomes exploitable.
