# Pluggable RAG components, Plugin SDK, and Model Evaluation framework

Three independent subsystems added to NEXUS: a RAG pipeline made composable through Protocol-based rankers, retrievers, and document parsers; a Plugin SDK with hook-based extensibility wired into the FastAPI lifespan; and a model evaluation framework with benchmark definitions, metric functions, and JSON reporting. The RAG extension maintains full backward compatibility by making new components optional constructor parameters. Watch for: the plugin loader inserts modules into `sys.modules` without cleanup on success (confirmed), the `HookManager.execute` is synchronous which blocks async hook handlers (confirmed), and the `HybridRetriever` merges on raw content strings which breaks when two documents have identical text (likely).

**Verdict**: APPROVED

## High-level view

The RAG pipeline's new components — rankers, retrievers, and parsers — are designed as drop-in Protocol implementations. `RAGPipeline` gains `from_config` for declarative assembly and delegates to custom components when present, falling through to its original behavior otherwise. The main risk is in the `CrossEncoderRanker` naming: it's not a cross-encoder at all, just BM25 + Jaccard overlap, which could confuse future developers about what capability is actually provided.

The Plugin SDK defines a clean lifecycle (load → hooks registered → unload → hooks removed) with error isolation at the hook execution layer and sandboxed filesystem imports for plugin modules. The sandboxed import pollutes `sys.modules` on success — plugin module names persist for the process lifetime with a `_nexus_plugin_` prefix — and the hook execution path is synchronous, meaning async hook handlers cannot be awaited and will silently return coroutines instead of executing.

The evaluation framework follows an adapter-function pattern where the evaluator is decoupled from specific LLMs. The pricing model in `cost_total` is hardcoded and the token estimation uses `chars/4` — acceptable for relative benchmark comparison but not reliable for absolute budgeting.

<details>
<summary>Issues (5)</summary>

1. **sys.modules pollution on successful plugin import** — `sandboxed_import` adds modules to `sys.modules` with a `_nexus_plugin_` prefix and never removes them on success. Over time this leaks references. Remove the module from `sys.modules` after `exec_module` completes, or document this as intentional for relative-import support.
2. **Synchronous HookManager cannot await async handlers** — `HookManager.execute` calls `handler.callback(context)` synchronously. Any async hook handler will return an unawaited coroutine, silently doing nothing. Either add an `async_execute` path or detect coroutines and await them.
3. **HybridRetriever merges results by content string** — If two distinct documents have identical text, their scores are collapsed. Use document index or a unique ID instead of raw content as the merge key.
4. **CrossEncoderRanker naming is misleading** — The implementation is BM25 + Jaccard overlap, not a cross-encoder. The docstring says "proxy" but the class name implies a capability that doesn't exist. Consider `CombinedScoreRanker` or similar.
5. **CodeParser regex patterns never used** — `_PATTERNS` is built in `__post_init__` but `_parse_python` and `_parse_js_ts` use line-by-line matching instead. The patterns are dead code occupying memory on every `CodeParser` instance.

## Plugin module lifecycle and sys.modules leak

In `plugin_loader.py`, `sandboxed_import` adds the module to `sys.modules` before calling `exec_module` (needed for relative imports within the plugin) but only removes it in the failure branches:

```python
sys.modules[module_name] = module
spec.loader.exec_module(module)
return module  # module stays in sys.modules forever
```

On error, `sys.modules.pop(module_name, None)` cleans up correctly. On success, the module persists. If plugins are loaded, unloaded, and reloaded, stale references accumulate. The fix is either to pop after exec (accepting that relative imports within the plugin may break after load) or to explicitly clean up in the unload path of `PluginRegistry.unregister`.

## Sync-only hook execution

`HookManager.execute` is the sole execution path:

```python
def execute(self, hook_point: HookPoint, context: HookContext) -> list[Any]:
    for handler in self._handlers[hook_point]:
        result = handler.callback(context)
        results.append(result)
```

If a plugin registers an async handler (`async def on_task(ctx): ...`), calling it synchronously returns a coroutine object — no exception is raised, no warning is logged, and the handler's body never executes. The plugin protocol's `get_hooks` signature says `Callable[..., Any]`, which admits async callables, but the execution engine silently discards them.

Two options: (1) inspect the return value with `asyncio.iscoroutine` and warn, or (2) provide `async execute()` that awaits coroutine results and falls through to sync call for non-coroutine handlers.

## HybridRetriever content-key collision

`HybridRetriever.retrieve` merges dense and sparse results into a dict keyed by `result["content"]`:

```python
merged: dict[str, dict[str, Any]] = {}
for result in dense_results:
    content = result["content"]
    merged[content] = { ... }
```

If two different documents share identical content (duplicates in the corpus, or templated text), the second overwrites the first. The document's index is available in the result dict — using `(content, index)` or just `index` as the key avoids this.

## Dead regex patterns in CodeParser

`CodeParser.__post_init__` builds `self._PATTERNS` — a dict of compiled regex patterns for Python, JavaScript, and TypeScript. But the actual parsing methods (`_parse_python`, `_parse_js_ts`) do their own line-by-line iteration with inline `re.match` calls and never reference `self._PATTERNS`. The patterns are compiled on every instantiation for no purpose.

## Test gaps

Not tested: the `from_config` class method in `RAGPipeline` with invalid or partial configs (only the happy path is exercised). The `sys.modules` cleanup gap is not tested — a plugin re-loaded after unload may get the stale cached module instead of a fresh import.
