# Sprint 4: Advanced Capabilities — Budget Incidents, A2A Router, Checkpoints, Provider Registry, Pipelines, Heartbeat Service

This sprint adds six new subsystems to the NEXUS platform: budget incident tracking with auto-pause on hard-stop breaches, a structured A2A router with three communication modes (notify/consult/delegate), durable execution checkpoints for crash recovery, an LLM provider registry with self-registration and task-based routing, a pipeline engine with enforced stage transitions and hooks, and a rich heartbeat run model with a service layer for liveness tracking. All six features are additive with no breaking changes to existing APIs — the existing 1081-test baseline passes, and 149 new tests bring the total to 1230.

Watch for: The ProviderRegistry singleton shares mutable class-level state across the process, which will collide when tests run in parallel or when reset() is called at module scope (confirmed). The A2A Router's execution chain grows without bound — there's no pruning, so long-lived router instances accumulate memory (confirmed). The HeartbeatRun model uses `datetime.utcnow()` (deprecated in Python 3.12) while the checkpoint and budget modules use timezone-aware `datetime.now(timezone.utc)`, creating inconsistency in timestamp comparison semantics (confirmed).

**Verdict**: APPROVED

## High-level view

The budget enforcer was extended in-place with multi-metric tracking (cost, tokens, API calls), lifetime window support, and a hard-stop path that creates incident records and fires callbacks. The key design decision is that `on_cost_event` checks all metrics after every event and fires hard-stop for the worst decision, meaning a single event can breach on tokens even though cost is fine. Enforcement is post-hoc — the overage is recorded before the DENIED decision fires.

The A2A Router is a separate module from the existing `a2a.py`, avoiding modification of a previously stable protocol layer. Permissions are open-by-default (everything allowed until the first permission is registered), which must be locked down before production deployment. The delegation chain grows without bound unless a CycleGuard is attached to cap it at 256.

The checkpoint system pairs a SQLModel table (`execution_checkpoints`) with an in-memory manager. The `recover_interrupted()` method deduplicates by task_id, returning only the latest active checkpoint per task — important for the startup recovery path where multiple checkpoints may exist for the same interrupted task.

The provider registry is a class-level singleton that auto-populates six providers at import time. Routing selects the first qualifying provider (not a scoring model), so result ordering depends on dict insertion order. The singleton's class-level `_providers` dict persists across tests unless explicitly reset, and the `@classmethod` API means the `__new__` singleton pattern is effectively dead code.

The pipeline engine enforces a directed graph of stage transitions with on_enter/on_exit hooks. If an `on_enter` hook raises, the transition has already been committed to the case — there is no rollback. Callers own PipelineCase instances; the engine stores no cases internally.

The heartbeat service uses `datetime.utcnow()` (naive) throughout, inconsistent with the timezone-aware timestamps in checkpoint and budget modules. Cross-module timestamp comparisons will raise `TypeError`.

## ProviderRegistry singleton and class-level state

The registry uses a class-level `_providers: dict[str, LLMProviderSpec] = {}` declaration shared across all test modules in the same process. The built-in providers self-register at module import time, so any import of the module populates the registry globally.

The `reset()` method sets `cls._instance = None` while clearing `_providers`. Since `_providers` is a class attribute, any code that obtained a reference to it before reset will see the empty dict — but new `__new__` calls recreate `_providers = {}` via the `if cls._instance is None` branch. This is fragile under pytest-xdist parallel execution where module-level side effects aren't isolated.

```python
class ProviderRegistry:
    _instance: "ProviderRegistry | None" = None
    _providers: dict[str, LLMProviderSpec] = {}  # shared across ALL instances

    def __new__(cls) -> "ProviderRegistry":
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._providers = {}  # resets on first instantiation only
        return cls._instance
```

The `register` and `route_to_provider` methods are all `@classmethod`, operating on class-level state regardless of whether anyone ever instantiates the class. The singleton `__new__` pattern is effectively dead code — the class methods bypass it entirely.

## A2A Router: unbounded delegation chain

Every delegate-mode message appends to `self._execution_chain`:

```python
self._execution_chain.append((message.sender, message.recipient))
```

There is no mechanism to truncate, reset, or prune this list. The CycleGuard's `MAX_ANCESTOR_DEPTH` (256) will raise `CycleGuardError` if the chain grows past 256 entries, but only if CycleGuard is attached. Without a CycleGuard, the chain grows indefinitely. For a router that lives for the duration of a long-running process, this is a slow memory leak.

## Timestamp inconsistency between heartbeat and checkpoint modules

`heartbeat_run.py` uses naive UTC:
```python
started_at: datetime = Field(default_factory=lambda: datetime.utcnow())
created_at: datetime = Field(default_factory=lambda: datetime.utcnow())
```

`heartbeat_service.py` also uses `datetime.utcnow()` for `last_output_at` and `finished_at`.

Meanwhile, `checkpoint.py` uses:
```python
created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
```

If any code compares a heartbeat timestamp with a checkpoint timestamp, Python raises `TypeError: can't compare offset-naive and offset-aware datetimes`. Within each module the timestamps are self-consistent, but this is a landmine for future integration code.

## Budget enforcer: post-hoc enforcement and the "total_cents" naming problem

The enforcement logic in `on_cost_event` records the spending *before* checking the budget:

```python
self._spent[key] += amount_cents
self._metrics[key]["tokens"] += tokens
# ... then check_can_spend(scope_type, scope_id, 0) -- already exceeded
```

This means `on_cost_event` fires DENIED only *after* the overage is recorded. `check_can_spend` as a pre-flight check can prevent overage; `on_cost_event` can only react to it. Callers expecting `on_cost_event` to reject the spend need to understand the budget is already consumed.

The `total_cents` parameter name is reused for all metrics: `set_budget(..., metric="api_calls", total_cents=100)` sets a budget of 100 API calls. The naming confusion is inherited from backward-compatibility constraints but could mislead callers.

## Pipeline engine: on_enter hook failure doesn't rollback

If an `on_exit` hook raises, the case has not yet transitioned — the exception propagates and the transition is effectively cancelled. But if an `on_enter` hook raises, the case has already transitioned:

```python
case.history.append(record)
case.current_stage_id = target_stage_id
case.updated_at = now
if new_stage.kind == StageKind.DONE:
    case.status = CaseStatus.COMPLETED
# on_enter fires AFTER state is committed
self._fire_hooks(target_stage_id, "on_enter", case, new_stage)
```

A failing `on_enter` hook leaves the case in the new stage with potentially incomplete side effects and no rollback path.
