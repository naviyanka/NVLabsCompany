# LLM integration for RAG embeddings, task planner, critic, and fact extraction

Four new modules wire real LLM calls into existing heuristic-based systems: vector embeddings for the RAG pipeline, LLM-driven task decomposition, LLM-powered quality evaluation with caching, and structured fact extraction with rate limiting. All four follow a dependency-injection pattern — accept an `async (str) -> str` callable — and fall back to existing heuristics on any failure. The implementation is backward-compatible: existing code paths work unchanged when no LLM provider is configured.

Watch for: unbounded cache growth in `LLMCriticEvaluator` (confirmed), a new httpx connection allocated per embedding API call in `OpenAIEmbeddingProvider` (confirmed), and prompt injection surface across all four modules where user-controlled text is interpolated into LLM prompts without sanitization (confirmed).

**Verdict**: APPROVED

## High-level view

The embedding system introduces a clean `EmbeddingProvider` protocol with three implementations — OpenAI (remote), Local (hash-based bag-of-words), and Fallback (thin wrapper over Local). The RAG pipeline's `search` method now computes real cosine similarity when embeddings exist and degrades to token-overlap when they don't, preserving the 0.7/0.3 BM25/vector weighting. The architectural limitation is that vector similarity is scored only for chunks that already passed the BM25 top-k filter, so purely semantic matches with no lexical overlap remain invisible.

The planner and critic modules accept a callable, send a structured prompt, parse JSON, validate the output, and fall back to the existing base class on any failure. The critic adds an unbounded in-memory cache keyed by `(task_id, sha256(result), criterion_name)` — appropriate for short-lived evaluator instances but a latent memory leak if the evaluator is long-lived or shared across many tasks.

The fact extractor adds a rolling-window rate limiter and a minimum-length threshold as cost guards, bypassing the LLM entirely for short texts. It deduplicates extracted facts within a single call but has no cross-call deduplication, meaning the same fact can be extracted repeatedly across separate invocations.

All four modules interpolate user-controlled content directly into prompt template strings via `.format()`. In the current deployment context (internal agent output), this is low-risk, but the surface exists and would become a prompt injection vector if any of these modules are exposed to untrusted input.

1. **Unbounded critic cache** — `LLMCriticEvaluator._cache` grows without eviction. Add a max-size bound or TTL, or document that evaluator instances should be short-lived.
2. **Prompt injection surface** — All four LLM modules interpolate untrusted text into prompts via `.format()`. Add a note or sanitization layer if these are ever exposed to external input.
3. **Per-call httpx client in OpenAI embeddings** — `OpenAIEmbeddingProvider._call_api()` creates and destroys an `httpx.AsyncClient` on every invocation, paying TLS handshake costs each time. Accept or reuse a client instance for batch workloads.
4. **BM25-gated vector search** — `RAGPipeline.search()` computes vector scores only for chunks already returned by the BM25 top-k filter. Purely semantic matches (no lexical overlap) are never surfaced. Consider a parallel vector-only path if the embedding provider is available.
5. **Rate limiter tracks only successes** — `LLMFactExtractor` appends to `_call_timestamps` only on success, so repeated failures don't count against the rate limit and a fast retry loop could flood the upstream LLM.

## Embedding providers and vector search integration

`OpenAIEmbeddingProvider._call_api()` creates a new `httpx.AsyncClient(timeout=60.0)` per call:

```python
async with httpx.AsyncClient(timeout=60.0) as client:
    response = await client.post(...)
```

`index_chunks()` calls `embed_batch()` which sends the full batch in one request, so the per-call client cost is paid once at index time. For search, `embed()` is called once per query — one extra TLS handshake per search. Acceptable for low-QPS, problematic for high-QPS deployments.

`RAGPipeline.search()` fetches all chunks for a company, runs BM25 over the full set, then scores only the BM25 top-k with vector similarity. Vector similarity only re-ranks results that already have some lexical match. If a query is semantically related but uses entirely different vocabulary, the relevant chunk won't appear in BM25 results and will never be scored by the vector path.

## LLM task planner: format-string fragility

The planner builds its prompt via `self._prompt_template.format(task_description=description, context=json.dumps(context, default=str))`. If the task description contains Python format-string metacharacters (`{`, `}`), this raises a `KeyError` or produces garbled output. The outer `except Exception` catches this and falls back — fail-safe — but tasks with curly braces in descriptions (common for code-related tasks) will silently never get LLM-based decomposition.

The default prompt template uses doubled braces `{{`/`}}` for its JSON example, which is correct. Custom templates must follow this convention, but the requirement isn't documented.

## LLM critic evaluator: unbounded cache and optimistic fallback

`LLMCriticEvaluator._cache` is a plain dict with no eviction strategy:

```python
self._cache: dict[tuple[str, str, str], float] = {}
```

If the evaluator instance is long-lived (e.g., stored on an application-level service), the cache grows linearly with the number of unique (task, result, criterion) triples evaluated. There's no upper bound.

The fallback heuristic in the base `CriticEvaluator._evaluate_criterion` scores optimistically (static 0.8 for correctness, length-based for completeness). A failed LLM call doesn't penalize the result — it inflates the score. If the LLM is down, everything passes. Whether fail-open is intentional should be documented.

## LLM fact extraction: rate limiter gaps

The rate limiter tracks only successful calls (`_call_timestamps.append` is inside the `try` block, after parsing succeeds). If the LLM repeatedly throws exceptions (network timeout, 500 errors), those calls aren't counted. A retry loop wrapping `extract_facts` could flood the upstream LLM without triggering the rate limit. Currently no retry logic exists in the codebase, so this is latent.

The prompt template uses `{text}` — a single placeholder. Agent output containing JSON or code snippets with curly braces will cause `.format()` to raise, triggering fallback to regex extraction every time for that class of input. This creates a systematic blind spot: code-heavy agent output never gets LLM extraction.

## Prompt injection surface

All four modules insert agent-generated text directly into prompt strings:

- `LLMTaskPlanner`: task description and context
- `LLMCriticEvaluator`: task description, result (stringified), and context
- `LLMFactExtractor`: the full agent output text

The LLM callable is an opaque function — consumers don't control how the prompt is presented to the model. If the callable wraps a completion endpoint without system/user separation, adversarial content in agent output could steer model behavior. This matches standard practice for LLM-integrated applications but should be documented as a known surface.

## Test coverage

Not tested: the format-string failure mode when input contains `{`/`}` characters; behavior when `embed_batch` is called with an extremely large list (no batching/chunking for the OpenAI API's input limit); the critic's behavior after thousands of cached entries; concurrent access to the rate limiter's `_call_timestamps` list (safe under asyncio's single-threaded model, but would break under threading).
