# Phase 2: Adapter Completeness and Fallback Infrastructure (v2)

This change adds four production-hardening features: streaming JSON parsing and session resumption for the Claude Code adapter, a subprocess-based MCP stdio transport with JSON-RPC communication, an embedding fallback path for semantic memory when mempalace is unavailable, and a Fernet-based secret backend with atomic file persistence and key rotation. All five v1 issues have been addressed: `InvalidToken` is caught in `decrypt()`, MCP stdio validates response IDs and skips notifications, the `_mining` flag is documented as sync-only, private API coupling is documented with rationale, and the hardcoded salt has an explanatory comment.

Watch for: `os.rename` in semantic memory's `_save_embeddings` fails on Windows if the target file exists (likely), `rotate_key` propagates `InvalidToken` if any ciphertext is corrupted mid-rotation leaving the store in an inconsistent state (possible), and `embed_batch` in the RAG pipeline has no error handling for embedding provider failures leaving `index_chunks` to crash mid-persist (likely).

**Verdict**: APPROVED

## High-level view

All v1 issues are resolved. The remaining concerns are non-blocking: an `os.rename`/`os.replace` inconsistency between the two atomic-write paths, an unguarded `embed_batch` call in the RAG indexer that should degrade gracefully on provider failure, and an edge case in `rotate_key` where a corrupted entry aborts the entire operation.

The semantic memory `_save_embeddings` uses `os.rename` where the secret backend uses `os.replace`. On Windows `os.rename` raises `FileExistsError` when the destination exists — a one-line fix for cross-platform consistency.

The RAG pipeline's `index_chunks` calls `await self.embedding_provider.embed_batch(chunks)` without a try/except. If the embedding provider raises (network error, rate limit), the method crashes before any chunks are persisted. Since `embed_batch` is called before the insertion loop, it's all-or-nothing rather than partial corruption — but callers expect indexing to degrade gracefully to BM25-only when embeddings are unavailable.

## Semantic memory: os.rename on existing files

`_save_embeddings` creates a temp file via `mkstemp` then calls `os.rename(tmp_path, str(path))`. The secret backend's equivalent uses `os.replace(tmp_path, str(self._persist_path))`. On POSIX both are atomic replacements, but on Windows `os.rename` raises `FileExistsError` when the target exists. Since `_save_embeddings` is called on every `mine_agent` invocation after the first (overwriting the existing embeddings.json), this would break on Windows.

## RAG pipeline: embed_batch error propagation

```python
embeddings: Optional[list[list[float]]] = None
if self.embedding_provider is not None and chunks:
    embeddings = await self.embedding_provider.embed_batch(chunks)
```

If `embed_batch` raises, `index_chunks` aborts without writing any chunks to the database. Wrapping the call in try/except and setting `embeddings = None` on failure would preserve the degraded-but-functional path — chunks indexed without embeddings, BM25 search still works. `OpenAIEmbeddingProvider._call_api` calls `response.raise_for_status()`, which throws `httpx.HTTPStatusError` on 4xx/5xx — a realistic failure mode for rate limits or quota exhaustion.

## rotate_key partial failure mode

`rotate_key` iterates `self._store.items()` and calls `self._fernet.decrypt(ciphertext)` on each entry without catching `InvalidToken`. A single corrupted entry (manual file editing, partial write recovery) aborts the entire rotation. The old key remains active and the store is unchanged, so there's no data loss — but the operator has no way to proceed without manually removing the corrupted entry from the persistence file.

## Test coverage gaps

Not tested: `embed_batch` failure during `index_chunks`, `os.rename` behavior when the target file already exists, and `rotate_key` with a corrupted entry in the store.
