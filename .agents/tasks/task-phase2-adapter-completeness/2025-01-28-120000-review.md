# Phase 2: Adapter Completeness and Fallback Infrastructure

This change adds four production-hardening features: enhanced streaming JSON parsing and session resumption for the Claude Code adapter, a new MCP stdio transport for subprocess-based server communication, an embedding fallback path in semantic memory when mempalace is unavailable, and a Fernet-based secret backend with atomic file persistence and key rotation. The approach is consistent across all four: each feature introduces a fallback or alternative path to an existing capability, uses protocol/interface patterns for pluggability, and includes atomic-write persistence where durability matters.

Watch for: `decrypt()` propagates `InvalidToken` exceptions unhandled after key rotation or corruption (confirmed), the MCP stdio transport doesn't match response IDs to request IDs so concurrent requests would interleave (confirmed), and the semantic memory `_mining` flag provides no actual concurrency protection in async code (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The Claude Code adapter now always passes `--output-format stream-json` and parses newline-delimited JSON events from stdout, extracting session IDs for resumption and result text for cleaner output. It also accepts `--resume` and `--worktree` flags via the payload dict. The change is backward-compatible: if the output isn't valid JSON, the original raw text flows through unchanged.

The MCP stdio transport (`StdioMCPTransport`) implements connect/list_tools/call_tool/disconnect over subprocess stdin/stdout using newline-delimited JSON-RPC. It uses a single `readline()` per request, which means it assumes strict request-response ordering — any notification or out-of-band message from the server would be consumed as the "response" and parsed incorrectly.

The semantic memory fallback re-uses `LocalEmbeddingProvider._compute_embedding` (a synchronous method accessed via a private name) to chunk and embed agent memory files into a JSON store when mempalace isn't on PATH. The chunking and search logic is straightforward cosine-similarity ranking.

The secret backend uses PBKDF2-HMAC-SHA256 (480K iterations) to derive a Fernet key from an application secret. Persistence uses temp-file-plus-`os.replace` for atomicity and sets 0o600 permissions. Key rotation decrypts all secrets with the old key and re-encrypts with the new one in a single pass. The `decrypt()` method does not catch `InvalidToken`, so callers receive an unhandled exception if the stored ciphertext was encrypted with a different key.

<summary>Issues (5)</summary>

1. **Unhandled InvalidToken in decrypt** — `FernetSecretBackend.decrypt()` lets `cryptography.fernet.InvalidToken` propagate to callers when ciphertext was encrypted with a different key (e.g., after rotation with stale data, or corruption). Wrap the decrypt call and return `None` on `InvalidToken` to match the method's documented return contract.
2. **MCP stdio response ID not validated** — `_send_request` reads the next line from stdout and assumes it corresponds to the last sent request. If the MCP server emits a notification or an out-of-order response, the client will misattribute it. Validate `response["id"] == request["id"]` or implement a pending-request map.
3. **Semantic memory `_mining` flag is not async-safe** — The boolean flag guarding `mine_all` prevents re-entry in single-threaded synchronous code, but `mine_agent` calls subprocess.run (blocking) or file I/O without yielding. In an async context where `mine_all` might be called from multiple coroutines, the flag offers no protection. Use `asyncio.Lock` or document that `mine_all` must only be called from a synchronous context.
4. **Private API coupling in semantic fallback** — `SemanticMemoryManager` calls `self._embedding_provider._compute_embedding(chunk)` directly (underscore-prefixed method on `LocalEmbeddingProvider`). This couples the fallback to an implementation detail. Use the public `embed()` method (requires making mine/search async, or adding a sync facade to the provider).
5. **Secret backend hardcoded salt** — `_SALT = b"nexus-integration-secrets"` is a module-level constant shared across all deployments. If two environments share a persistence file (e.g., via a shared mount), secrets from one environment are decryptable in the other if they share the application secret. Consider deriving the salt from a deployment-specific value or making it configurable.

## Claude Code adapter: stream-json parsing and session resumption

The adapter unconditionally adds `--output-format stream-json` to every invocation. Non-JSON output (from older Claude Code versions that don't support stream-json) produces an empty events list, causing the code to fall through to using raw `stdout_text` — backward-compatible by construction. However, if an older CLI rejects `--output-format` as an unknown flag and exits non-zero, the task would be reported as failed rather than falling through gracefully.

Session IDs are extracted from `system` or `result` event types and stored in `session.metadata["last_session_id"]`. The session ID is persisted only in the in-memory session object, so it doesn't survive process restarts — sufficient for single-run tasks, but insufficient for long-lived agent workflows that expect resumption across restarts.

## MCP stdio transport: request-response ordering assumption

`_send_request` writes a JSON-RPC message to stdin, then calls `readline()` on stdout exactly once. The transport increments `_request_id` monotonically but never checks that the response's `id` field matches the request. The MCP protocol allows servers to emit notifications (no `id` field) and the transport has no mechanism to skip them.

```
client → {"jsonrpc":"2.0","id":2,"method":"tools/call",...}
server → {"jsonrpc":"2.0","method":"notifications/progress",...}  ← consumed as response to id:2
server → {"jsonrpc":"2.0","id":2,"result":{...}}                  ← never read
```

If any MCP server emits progress notifications (common in long-running tools), the transport will parse the notification as the response and return garbage or raise on missing keys. The fix is to loop `readline()` until a message with a matching `id` is received, buffering notifications.

## Semantic memory fallback: synchronous embedding in async context

The fallback calls `self._embedding_provider._compute_embedding(chunk)` — a synchronous method accessed by private name. `LocalEmbeddingProvider` exposes a public async `embed()` method, but `mine_agent` and `_search_fallback` are synchronous. This creates a design tension: the semantic manager is synchronous (it wraps subprocess calls with `subprocess.run`), but the embedding provider's public API is async.

The `_mining` flag in `mine_all` is a re-entry guard, not a concurrency primitive. It prevents recursive calls within the same call stack but provides no protection against concurrent coroutines or threads. Since `mine_agent` calls `subprocess.run` (which blocks the event loop), running `mine_all` from an async context would block the loop entirely — the flag is a secondary concern compared to the blocking I/O.

The chunking logic splits on `\n\n` first, then subdivides large paragraphs by fixed 500-character boundaries. Mid-word splits are possible at chunk boundaries, which could degrade embedding quality for boundary text.

## Secret backend: decrypt crash after key rotation

`decrypt()` calls `self._fernet.decrypt(ciphertext)` without catching `InvalidToken`. The docstring promises "None if not found or unavailable," but a corrupted or mis-keyed ciphertext raises an exception that propagates to the caller. The test suite confirms this: `test_rotate_key_old_key_cannot_decrypt` explicitly asserts `pytest.raises(InvalidToken)` on decrypt.

After a key rotation, if another process loads the persistence file with the old key (race condition, stale instance, deployment overlap), every `decrypt()` call throws. Adding a try/except around the decrypt to catch `InvalidToken` and return `None` would align with the documented contract and fail-closed semantics.

## Test coverage

Not tested: MCP transport behavior when server emits notifications between responses, `decrypt()` behavior with corrupted ciphertext (except indirectly via old-key test), semantic memory behavior under concurrent `mine_all` calls, and the adapter's behavior when Claude Code doesn't support `--output-format stream-json` (returns a non-zero exit code with an "unknown flag" error rather than falling through to text output).
