# External agent adapters, identity system, and workflow delegation

This change adds the runtime layer that connects NEXUS's orchestration to actual AI execution backends. Six adapter implementations (OpenAI, Anthropic, Ollama, Claude Code, HTTP, MCP) sit behind a `BaseAdapter` ABC that standardizes session management, cost tracking, and error handling. On top of these, a Soul/Persona identity system assembles per-agent context within token budgets, and a `CompanyWorkflow` + `TaskFlow` pair implements governed delegation (CEO → CTO → Engineer → QA). A demo bootstrapper creates "NexusCorp" with five named agents, and 15 new API endpoints expose the full stack over HTTP.

Watch for: API credentials are passed in request bodies and stored in plain dicts without encryption or scrubbing (confirmed). `BaseAdapter.terminate` removes tracking state but leaves cost/artifact/log dicts behind (confirmed). The `CompanyWorkflow` and `TaskFlow` _do_execute methods produce hardcoded success results—they never invoke real adapters—so the claimed integration between workflows and adapters is not yet wired (confirmed). Module-level `importlib.util.spec_from_file_location` hacks bypass package structure in a way that will silently shadow real module registration (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The adapter abstraction is cleanly layered: `BaseAdapter` provides the session/cost/error framework, subclasses only override `_do_execute` and `validate_config`, and the registry enables plugin-style extension. The design is sound.

The critical gap is that `CompanyWorkflow._engineers_execute` and `TaskFlow._do_execute` both return hardcoded success dicts and never call an actual adapter. The delegation chain is structurally complete but execution is simulated—there is no runtime bridge from workflow steps to `AdapterRegistry.create_adapter` → `adapter.execute_task`. The `TaskFlow` constructor accepts no adapter registry or factory.

The API layer (three new route modules) duplicates domain knowledge by re-implementing soul templates and adapter capability maps as inline dicts rather than importing from the domain modules. Divergence is inevitable and undetectable.

The `importlib.util.spec_from_file_location` pattern in `base.py` and `mcp_adapter.py` sidesteps missing `sqlalchemy` at import time but introduces fragile coupling to file paths and races with normal import resolution.

API key handling is purely structural (validate presence, pass to httpx headers) with no masking, rotation, or scrubbing from logs/artifacts. The HTTP adapter stores built auth headers in `session.metadata["headers"]`—a dict that persists and could leak through metadata inspection.

`Persona._store` is a class-level dict with no eviction, size limit, or per-company isolation—it grows monotonically in a long-lived server.

## BaseAdapter session lifecycle leak

When `terminate()` is called, only `self._sessions` is cleaned:

```python
async def terminate(self, session: AgentSession) -> bool:
    if session.session_id in self._sessions:
        await self._do_terminate(session)
        session.status = AgentStatus.TERMINATED
        self._add_log(session.session_id, "Session terminated")
        self._sessions.pop(session.session_id, None)
        return True
    return False
```

`_cost_tracking`, `_artifacts`, `_logs`, and `_conversation_history` retain entries keyed by `session_id` indefinitely. In a long-running server, these dicts grow monotonically. The post-terminate `_add_log` call succeeds because `_logs` hasn't been cleaned—creating an inconsistency where a terminated session still accumulates log data.

## Workflow-adapter integration is not wired

`CompanyWorkflow._engineers_execute`:

```python
# Simulate execution result
result = {
    "task_id": task.get("task_id"),
    "status": "completed",
    "output": f"Completed: {task.get('description', '')}",
    "cost_cents": task_cost,
}
```

`TaskFlow._do_execute`:

```python
# Simulated execution - in production this calls the actual adapter
result = {
    "task_id": execution.task_id,
    "agent_id": agent["agent_id"],
    "adapter_type": agent["adapter_type"],
    "output": f"Executed task {execution.task_id}",
    "status": "success",
}
return True, result
```

There is no mechanism (method override, callback, adapter injection) for plugging in real execution. The `TaskFlow` class accepts no adapter registry or factory in its constructor. The demo scenarios exercise governance logic but cannot invoke any model—they are pure state-machine walkthroughs. If the intent is a working demo against Ollama (zero-cost local), the wiring is missing.

## Credential handling in adapter config

The OpenAI and Anthropic adapters receive `api_key` in the `config` dict and pass it directly to httpx headers. The same config dict is stored in `AgentSession.config`, accessible from `BaseAdapter._sessions[session_id].config`. No adapter scrubs the API key from logs or metadata.

The HTTP adapter is worse: it builds headers including `bearer_token` and stores them in `session.metadata["headers"]`—persisting for the session's lifetime and potentially leaking through metadata inspection routes.

## importlib spec_from_file_location fragility

```python
if "nexus.runtime.adapter" not in sys.modules:
    _adapter_path = (
        pathlib.Path(__file__).parent.parent / "runtime" / "adapter.py"
    )
    _spec = importlib.util.spec_from_file_location(
        "nexus.runtime.adapter", str(_adapter_path)
    )
```

This assumes a specific filesystem layout relative to the current file. It will break if the package is installed from a wheel, vendored at a different path, or tested with non-standard `sys.path`. It also sets `sys.modules` globally, so any later normal import of `nexus.runtime.adapter` gets the raw-loaded version without `nexus.runtime.__init__` having executed.

A simpler approach: `try: from nexus.runtime.adapter import ... except ImportError: ...` with a clear error.

## API route template duplication

`routes/identity.py` defines soul templates as inline dicts while `identity/soul.py` has `SOUL_TEMPLATES` with the authoritative definitions. If a template is modified in `soul.py`, the API response shows stale values. Same pattern in `routes/adapters.py` which hardcodes adapter capabilities rather than calling `AdapterRegistry().get_capabilities(adapter_type)`.

## httpx.AsyncClient per retry attempt

Both OpenAI and Anthropic adapters create a new `httpx.AsyncClient` for each retry:

```python
for attempt in range(MAX_RETRIES):
    async with httpx.AsyncClient(timeout=120.0) as client:
        response = await client.post(...)
```

5 retries = 5 TCP connection setups with no reuse. Under rate-limit conditions (where retries are most likely), this multiplies connection overhead. The HTTP adapter's `_poll_for_result` does the same per-poll iteration.

## Test coverage gaps

Not tested:
- Actual httpx calls (by design—no network), meaning retry logic and response parsing are untested beyond structural correctness
- `_poll_for_result` polling loop in HTTPAdapter
- Claude Code subprocess timeout/SIGTERM/SIGKILL path
- MCP adapter tool discovery and sequential execution (no MCPClient mock constructed)
- `WorkflowTrace` cost accumulation across multiple engineer steps with budget enforcement
- Persona memory eviction under extreme token pressure (budget smaller than a single memory entry)
