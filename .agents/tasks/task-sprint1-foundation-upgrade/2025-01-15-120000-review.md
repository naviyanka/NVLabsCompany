# Sprint 1 foundation: CLI multi-backend adapter, guardrail chain, template registry, persistent circuit breaker

This change adds four foundational subsystems to NEXUS: a generalized CLI adapter that routes prompts to multiple AI coding backends (claude, codex, aider, kiro, opencode, agy) via subprocess; a composable async guardrail chain with Protocol-based design, fail-fast, and fail-closed semantics; a YAML-frontmatter template registry for agent roles; and a database-backed circuit breaker that persists state across restarts. The approach consistently follows existing patterns — BaseAdapter extension, SQLModel persistence, in-memory + DB dual-layer governance. Watch for: the persistent circuit breaker never checks its own cooldown_seconds field, meaning open circuits stay open permanently until manual reset or a success (confirmed); the lifespan block loads kill switch state but does not restore circuit breaker state into any runtime structure (confirmed); and API keys are exposed to all backends via `os.environ.copy()` in the CLI adapter (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The CLI adapter introduces a registry-driven pattern where `CLIBackendInfo` data objects describe how each backend wants its arguments constructed — whether prompts go via stdin or positional args, which flags to pass, which env vars to strip. The `_build_args` dispatch is a hardcoded `if/elif` chain keyed on backend id rather than a strategy on the `CLIBackendInfo` itself; this works for six backends but will scale poorly.

The guardrail chain is intentionally separate from the existing `governance/guardrails.py`. It adds async support, fail-closed exception handling, and Protocol-based composition that the older module lacks. The two modules export overlapping names (`GuardrailResult`, `StructuralGuardrail`) into different import paths — not a runtime conflict, but a maintenance hazard when other code needs to decide which to import.

The persistent circuit breaker mirrors `PersistentKillSwitch` structurally but omits the half-open / cooldown-expiry logic that the in-memory `CircuitBreaker` already implements. The `cooldown_seconds` column is stored and loaded but never consulted by `is_open()` — an open circuit stays open until an explicit `record_success()` or `reset()`. This is the most significant behavioral gap in the change.

The lifespan wiring loads kill switches into the in-memory `kill_switch_registry` (which is checked per-request by middleware), but does not load circuit breaker state into the in-memory `CircuitBreaker` or any other runtime structure. After a restart, open circuits exist in the DB but nothing enforces them until the next `is_open()` DB query.

<summary>Issues (6)</summary>

1. **Circuit breaker cooldown ignored** — `PersistentCircuitBreaker.is_open()` returns True for any open circuit regardless of cooldown_seconds. Add a time check: if `now - opened_at >= cooldown_seconds`, auto-close the circuit (matching the in-memory behavior in `kill_switch.py:296-318`).
2. **Circuit breaker state not loaded at startup** — The lifespan calls `persistent_ks.load_active()` for kill switches but never instantiates or calls `PersistentCircuitBreaker.load_state()`. Open circuits from a previous run are not enforced until something queries the DB for a specific agent.
3. **API keys leaked to subprocess environment** — `CLIAdapter._do_execute` copies `os.environ` into the child process, which includes `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, and any other secrets. Only `backend.delete_env` vars are stripped. Consider an allowlist or at minimum strip the API keys for backends that don't need them.
4. **Temp workspace not cleaned up** — `_do_terminate` removes the session from `_workspaces` but does not delete the tempdir created by `tempfile.mkdtemp`. Long-running systems will accumulate abandoned workspace directories.
5. **`_build_args` is a hardcoded dispatch** — Adding a seventh backend requires editing the adapter source. Consider moving argument construction logic into `CLIBackendInfo` (a `build_args` method or template pattern) so new backends only require registry entries.
6. **Dual guardrail modules with overlapping exports** — `nexus.guardrails` and `nexus.governance.guardrails` both export `GuardrailResult` and `StructuralGuardrail`. Document the intended migration path or deprecation plan to prevent confusion.

## Persistent circuit breaker: cooldown is stored but never enforced

The `cooldown_seconds` field exists on the model and is faithfully persisted, but `is_open()` performs only:

```python
stmt = select(CircuitBreakerRecord).where(
    CircuitBreakerRecord.agent_id == agent_id,
    CircuitBreakerRecord.is_open == True,
)
result = await session.execute(stmt)
return result.scalar_one_or_none() is not None
```

No comparison against `opened_at + cooldown_seconds` vs. current time. The in-memory `CircuitBreaker` (in `kill_switch.py`, lines 296-318) explicitly checks elapsed time and transitions to half-open when the cooldown elapses. The persistent version does not replicate this, so an agent whose circuit opened will remain permanently blocked until something calls `record_success()` or `reset()`. In an autonomous system where agents may not be retried automatically, this means a single bad run could permanently disable an agent post-restart.

## Lifespan loads kill switches but not circuit breaker state

The new lifespan code:

```python
persistent_ks = PersistentKillSwitch(async_session_factory)
loaded_count = await persistent_ks.load_active()
```

This syncs kill switch state into the in-memory middleware registry (which is checked on every HTTP request). No equivalent call exists for circuit breakers. `PersistentCircuitBreaker.load_state()` returns a dict, but nothing consumes it. If the intent is for callers to individually query `is_open()` per-agent on each execution attempt (bypassing any in-memory cache), the startup load is unnecessary — but then the `load_state()` method exists without a consumer.

## CLI adapter environment handling and secrets exposure

`_do_execute` copies the entire process environment:

```python
env = os.environ.copy()
for var in backend.delete_env:
    env.pop(var, None)
```

The `delete_env` list is empty for all default backends. This means every subprocess inherits `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `SECRET_KEY`, `DATABASE_URL`, and anything else in the parent process. For backends like `aider` or `agy` that are third-party CLI tools, this leaks credentials those tools don't need and shouldn't have access to.

## Temp workspace lifecycle

When no explicit workspace is provided, the adapter creates a temp directory:

```python
workspace_path = tempfile.mkdtemp(
    prefix=f"nexus_cli_{backend_id}_{session.session_id[:8]}_"
)
```

`_do_terminate` removes the session from `self._workspaces` but never calls `shutil.rmtree` on the temp directory. If sessions are created and terminated at volume (which is the stated design intent for multi-backend execution), these directories accumulate indefinitely.

## `_build_args` dispatch structure

`CLIBackendInfo` already holds metadata about stdin support, command, and other capabilities, but the argument construction logic lives in the adapter as a six-branch `if/elif`:

```python
if backend.id == "claude":
    cmd.append("--print")
elif backend.id == "codex":
    cmd.append("--quiet")
    cmd.append(prompt)
...
```

This means the current "registry-driven" architecture is partially undone by the hardcoded dispatch. A `build_args` callable on `CLIBackendInfo` (or a simple template/format-string system describing flag placement) would let new backends be added without touching `cli_adapter.py`.

## Guardrail module overlap

The new `src/nexus/guardrails/` package and the existing `src/nexus/governance/guardrails.py` both define `GuardrailResult`, `StructuralGuardrail`, and a Protocol type (one named `Guardrail`, the other `GuardrailProtocol`). Both are importable, neither deprecates the other. The FEAT-002 spec says "The existing governance/guardrails.py should remain unchanged for backward compatibility," which is reasonable for this sprint, but without a documented migration path this creates a naming puzzle for any code that needs guardrails going forward.
