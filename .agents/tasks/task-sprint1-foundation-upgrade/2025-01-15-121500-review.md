# Sprint 1 foundation v2: all six v1 concerns addressed

This is the second review pass of the sprint 1 foundation change (CLI multi-backend adapter, async guardrail chain, template registry, persistent circuit breaker). All six issues from the first review have been resolved: cooldown is now enforced with auto-reset in `is_open()`, circuit breaker state is loaded alongside kill switches at startup, sensitive env vars are stripped via a hardcoded denylist plus per-backend `allow_env`, temp workspaces are cleaned in `_do_terminate`, `_build_args` delegates to backend subclasses, and the legacy guardrails module carries a deprecation docstring. Watch for: the loaded circuit breaker states at startup are not connected to any runtime enforcement mechanism — `cb_states` is logged but discarded, so enforcement depends entirely on per-call DB queries via `PersistentCircuitBreaker.is_open()` (confirmed); the sensitive env denylist is a static list that will silently miss new secrets added to the process environment (likely).

**Verdict**: APPROVED

## High-level view

The CLI adapter's environment handling now strips a hardcoded list of nine sensitive variable names (API keys, DATABASE_URL, tokens) unless a backend declares them in `allow_env`. This operates as a denylist rather than an allowlist — any new secret added to the parent process that isn't in `_SENSITIVE_ENV_PATTERNS` will leak through. The `allow_env` mechanism on `CLIBackendInfo` (e.g., claude gets `ANTHROPIC_API_KEY`, codex gets `OPENAI_API_KEY`, aider gets both) correctly scopes credentials to backends that need them.

The persistent circuit breaker now checks `opened_at + cooldown_seconds` against current time in `is_open()`, auto-closing expired circuits. The startup lifespan loads both kill switches and circuit breaker state, but with an asymmetry: kill switches sync into the in-memory registry enforced by middleware on every request, while circuit breaker states are loaded into a local variable, logged for count, and discarded. CB enforcement relies on each caller issuing a DB query through `PersistentCircuitBreaker.is_open()` — the startup load serves no runtime purpose beyond the log line.

The guardrail module deprecation is handled via a module-level docstring on `governance/guardrails.py` directing users to `nexus.guardrails`. No runtime `DeprecationWarning` is emitted on import, so code importing the old module will continue to work silently without any signal that it should migrate.

## Circuit breaker startup load is observability-only

The lifespan code instantiates `PersistentCircuitBreaker`, calls `load_state()`, and uses the result solely for a log line:

```python
persistent_cb = PersistentCircuitBreaker(async_session_factory)
cb_states = await persistent_cb.load_state()

_logger.info(
    "Governance state loaded from DB (%d active kill switches, "
    "%d open circuit breakers)",
    loaded_count,
    len(cb_states),
)
```

Compare to the kill switch path, which calls `kill_switch_registry.activate(record.company_id)` for each loaded record — actively populating the in-memory structure that middleware checks on every request. The circuit breaker has no equivalent injection. `cb_states` is a local variable that goes out of scope immediately. No production code path queries an in-memory circuit breaker; every check goes through `PersistentCircuitBreaker.is_open()` which hits the DB directly. The startup load either needs a consumer or should be replaced with a simple count query.

## Sensitive env denylist naming mismatch

The variable is named `_SENSITIVE_ENV_PATTERNS` but the implementation uses exact string matching (`env.pop(sensitive_var, None)`), not regex or glob patterns:

```python
_SENSITIVE_ENV_PATTERNS: list[str] = [
    "OPENAI_API_KEY",
    "ANTHROPIC_API_KEY",
    "SECRET_KEY",
    "DATABASE_URL",
    "DB_PASSWORD",
    "AWS_SECRET_ACCESS_KEY",
    "GITHUB_TOKEN",
    "GITLAB_TOKEN",
    "NEXUS_SECRET_KEY",
]
```

A variable named `OPENAI_API_KEY_BACKUP` or `MY_SECRET_KEY` would not be stripped. The mismatch between name ("patterns") and behavior (exact match) could mislead future maintainers into thinking substring or regex matching is active.

## `datetime.utcnow()` usage

Throughout `persistent_circuit_breaker.py`, timestamps are generated with `datetime.utcnow()`. Python 3.12 deprecated this in favor of `datetime.now(timezone.utc)` (which the in-memory `CircuitBreaker` in `kill_switch.py` already uses). The `CircuitBreakerRecord` model's default factory also uses `datetime.utcnow()`. Since this project targets 3.12+, aligning now avoids a future migration task.
