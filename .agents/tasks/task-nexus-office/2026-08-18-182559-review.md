# 2D Virtual Office visualization for the NEXUS dashboard

A full-page interactive office floor plan that renders agents as avatars in department rooms, with pan/zoom canvas, delegation flow arrows, meeting rooms, activity ticker, and a mobile list fallback. The visualization is purely derived from existing API data (agents + tasks) via polling, with no new backend endpoints. Fourteen new files implement the spatial layout, avatar rendering, SVG delegation overlays, and office controls; two existing files receive minimal routing additions.

Watch for: `useAgentMovement` hook is exported but never consumed — the same logic is duplicated inside `useOffice` (confirmed). The `statusColors` map references `paused` and `terminated` statuses that don't exist in the `AgentStatus` union type, creating dead styling branches (confirmed). The `OfficeCanvas` wheel handler calls `e.preventDefault()` which will throw a passive-event-listener error in Chrome since React attaches wheel listeners as passive by default on the root (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The spatial engine is entirely CSS-positioned divs with a CSS `transform: translate3d + scale` wrapper — no Canvas/WebGL/SVG for layout — keeping the rendering model simple and DOM-inspectable. Agent positions are recomputed every render cycle from API data using `useMemo`; there's no incremental position diffing, which is fine for the stated 50-agent ceiling but means the canvas re-lays-out fully on every poll tick when any agent or task changes.

The data pipeline fetches agents and tasks through existing `useApi` + `usePolling` hooks (10-second interval), then derives delegation arrows from parent-task relationships and fabricates meetings from a heuristic ("any 2+ busy agents = a sprint planning meeting"). Events are similarly synthesized from recently-completed tasks. This means the visualization will look the same on any instance with zero API data — there are no meeting or event endpoints backing these constructs.

Agent-to-room assignment uses keyword matching against `role` and `title` fields (`departmentRoomMap`). An agent whose role/title contains none of the ~12 configured keywords falls through to "common area." This is reasonable for demo purposes but produces a catch-all bucket that could grow large silently.

The `AgentMovement.tsx` file exports a `useAgentMovement` hook and a no-op component, but neither is imported anywhere in the codebase. The identical positioning logic lives in `useOffice.ts` (`computeAgentPositions`). This is dead code that adds confusion about where the canonical position computation lives.

## Dead `AgentMovement` module and duplicated position logic

`AgentMovement.tsx` exports `useAgentMovement` (a hook) and `AgentMovement` (a component that renders `null`). Neither is imported anywhere in the codebase. The position-computation logic it contains — grouping agents by room, arranging them in a grid, placing meeting participants in a circle — is replicated nearly line-for-line inside `useOffice.ts` in the `computeAgentPositions` function.

The duplication means a future developer could fix a positioning bug in one location and miss the other. Since `useOffice` is the one actually consumed by the page, `AgentMovement.tsx` is dead code. It should either be deleted or wired in as the canonical implementation (having `useOffice` call `useAgentMovement` internally).

## Status type mismatch between `AgentStatus` and office color maps

The `AgentStatus` type from `common.ts` is a union of five members:

```typescript
type AgentStatus = 'active' | 'idle' | 'busy' | 'offline' | 'error';
```

The `statusColors` map in `officeLayout.ts` includes entries for `paused` and `terminated`:

```typescript
paused: '#f59e0b',
terminated: '#9ca3af',
```

These keys can never match an actual agent's `status` field as typed. The avatar ring will fall through to the fallback (`statusColors.idle` = blue) for any status that isn't in the map, so no runtime crash occurs, but it's dead config that suggests the code was written against a different (or future) status model. Either extend `AgentStatus` or remove the unreachable entries.

## Passive wheel event and `preventDefault`

`OfficeCanvas` handles zoom via an `onWheel` React synthetic event handler that calls `e.preventDefault()`:

```tsx
const handleWheel = useCallback(
  (e: React.WheelEvent) => {
    e.preventDefault();
    const delta = e.deltaY > 0 ? -0.1 : 0.1;
    const newZoom = Math.max(0.3, Math.min(2.5, zoom + delta));
    onZoomChange(newZoom);
  },
  [zoom, onZoomChange]
);
```

In Chrome (and all Chromium-based browsers), wheel events registered through `addEventListener` on document/root are passive by default. React's synthetic event system registers the wheel listener on the root element with the browser's default options, which means `preventDefault()` is a no-op and logs a warning: `Unable to preventDefault inside passive event listener invocation`. The page will still scroll behind the canvas while zooming.

The fix is to attach the listener imperatively via a `useEffect` on the container ref with `{ passive: false }`:

```tsx
useEffect(() => {
  const el = containerRef.current;
  if (!el) return;
  const handler = (e: WheelEvent) => { e.preventDefault(); /* zoom logic */ };
  el.addEventListener('wheel', handler, { passive: false });
  return () => el.removeEventListener('wheel', handler);
}, [zoom, onZoomChange]);
```

## Fabricated meetings and events

`computeMeetings` creates a fake "Sprint Planning" meeting whenever two or more agents have `status === 'busy'`:

```typescript
if (busyAgents.length >= 2) {
  meetings.push({
    id: 'meeting-active-1',
    roomId: 'meeting-room-1',
    title: 'Sprint Planning',
    type: 'planning',
    participantIds: busyAgents.slice(0, Math.min(4, busyAgents.length)).map((a) => a.id),
  });
}
```

This is a pure fabrication — the underlying API has no meetings endpoint in this dashboard's `api/` directory. The result is that the meeting room will almost always show a meeting when there's any active work (since multiple agents being busy is common), or show nothing when the team is idle. It gives a misleading sense of live collaboration.

Similarly, `generateEvents` constructs ticker items from recently-completed tasks and delegation relationships. These are legitimate derivations from real data, unlike the meetings heuristic, and provide useful ambient information.

## Duplicate tasks fetch

`Office.tsx` calls `useApi<PaginatedResponse<Task>>(() => tasksApi.list(COMPANY_ID, { page_size: 100 }), [COMPANY_ID])` directly, while also calling `useOffice()` which internally makes the same API call with the same parameters. Both requests fire on mount and both poll independently. The `useOffice` hook already returns the computed `officeState` (which includes delegation arrows derived from tasks) and could expose the raw tasks array. The page component uses the second fetch to build `taskMap` for the mobile view and for `FloorPlan`, but these could be fed from the hook's internal data.

## Night mode partial implementation

The night mode toggle changes the canvas background to `bg-slate-900` and switches grid line colors from `#e5e7eb` to `#334155`. However, the overlay panels (`StatusPanel`, `OfficeControls`, `ActivityTicker`) remain white/light regardless of mode — they use hardcoded `bg-white/95` backgrounds and light-theme text colors. Room backgrounds also stay their pastel colors. The result is a dark canvas with bright floating panels and bright rooms, which looks visually inconsistent rather than like a deliberate "night" mode. This is cosmetic per the spec, so it's non-blocking, but worth noting as incomplete polish.
