# Phase 2: Communication, Knowledge, Meetings, Company Simulation, and Evolution Engine

NEXUS gains five new modules (communication, knowledge, meetings, company simulation, evolution) comprising 15 SQLModel classes, ~40 service classes, five API route modules registered in `main.py`, and 179 test methods. The architecture keeps a clean separation between service-layer logic (in-memory + optional DB persistence) and a thin CRUD API layer that delegates to SQLAlchemy. All promotion paths in the evolution engine enforce the governance gate via `ValueError` on missing `approval_id`.

Watch for: SQL injection via unescaped `ilike(f"%{query}%")` interpolation in knowledge routes (confirmed). Delegation API endpoint doesn't persist state — `POST /delegations` returns a fabricated response and `GET /delegations` always returns `[]` (confirmed). The `get_change_history` on the `ChangePromoter` service class ignores its `company_id` parameter and returns all records (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The governance gate — the single most critical safety invariant — is implemented correctly across all three promotion surfaces (`ChangePromoter.promote`, `SkillEvolution.promote_version`, `AgentEvolution.promote_candidate`). The API layer doubles down: `PromoteRequest` declares `approval_id: uuid.UUID` (non-optional Pydantic field), so a null value is rejected before reaching the service. Tests explicitly verify the `ValueError` path. However, the `promote_proposal` route doesn't check the proposal's current status — a "rejected" proposal can be promoted by anyone with a valid UUID.

The knowledge search routes (`list_pages`, `rag_search`, `search_experiences`) interpolate user-supplied strings directly into `ilike()` calls. SQLAlchemy parameterizes values, so this is not classic SQL injection — but the `%` and `_` wildcard characters in user input are not escaped, which produces incorrect search results and could be abused for DoS-grade pattern matching against large tables.

The company simulation delegation API is scaffolding: `delegate_task` constructs and returns a response object without writing anything to the database, and `list_delegations` returns a hardcoded empty list. The API surface is publicly registered and returns 201 Created, which implies persistence to callers.

Multi-tenant isolation is enforced at the query level: every `SELECT` where-clauses `company_id`, and models carry `company_id` as an indexed foreign key. The one gap is `ChangePromoter.get_change_history()`, which receives `company_id` but ignores it when returning in-memory records.

## Unescaped LIKE wildcards in knowledge search

In `src/nexus/api/routes/knowledge.py`, three endpoints pass user input directly into `ilike(f"%{query}%")`:

```python
# list_pages
stmt = stmt.where(KnowledgePage.title.ilike(f"%{query}%"))

# rag_search
.where(KnowledgeChunk.content.ilike(f"%{body.query}%"))

# search_experiences
stmt = stmt.where(ExperienceRecord.lessons_learned.ilike(f"%{query}%"))
```

SQLAlchemy will parameterize the value, so this doesn't produce injection of SQL structure. However, the LIKE-specific wildcards `%` and `_` are not escaped, meaning a user who sends `query=%` will match every row in the table, and `query=___` will match all 3-character content. In a knowledge base that could grow large, this is both a correctness bug and a potential performance issue. The fix is a two-line helper that escapes `%` → `\%` and `_` → `\_` before wrapping in the wildcard pattern.

Confidence: **confirmed** — the f-string interpolation is visible in the route code.

## Delegation API is non-functional

`delegate_task` in `company_sim.py` creates a `DelegationResponse` from request fields without touching the database:

```python
async def delegate_task(...) -> Any:
    delegation_id = uuid.uuid4()
    now = datetime.now(timezone.utc)
    return DelegationResponse(
        id=delegation_id,
        task_id=body.task_id,
        ...
    )
```

The corresponding `list_delegations` endpoint returns `[]`. A client that POSTs a delegation and then GETs the list will see nothing.

Confidence: **confirmed** — the route body creates no DB objects.

## `ChangePromoter.get_change_history` breaks tenant isolation

```python
async def get_change_history(self, company_id: uuid.UUID) -> list[dict[str, Any]]:
    # In production, this would query the DB filtered by company_id
    # For now, return all tracked promotions
    return self._promotions
```

The comment acknowledges the gap but the method is callable today. If two companies share the same `ChangePromoter` instance, one company could see the other's promotions.

Confidence: **confirmed** — the parameter is unused in the return path.

## Meeting `agent_id` query parameter is accepted but ignored

`list_meetings` in `meetings.py` declares `agent_id: Optional[uuid.UUID] = None` as a query parameter but the function body only filters on `status_filter` and `meeting_type`:

```python
stmt = select(Meeting).where(Meeting.company_id == company_id)
if status_filter:
    stmt = stmt.where(Meeting.status == status_filter)
if meeting_type:
    stmt = stmt.where(Meeting.meeting_type == meeting_type)
```

To filter by participant, the route would need a join to `MeetingParticipant`. Currently, passing `agent_id` is silently ignored.

Confidence: **confirmed** — no conditional on `agent_id` in the query builder.

## `promote_proposal` API lacks status pre-condition check

The route transitions any proposal to "promoted" regardless of its current status:

```python
proposal.status = "promoted"
proposal.approval_id = body.approval_id
```

A proposal that is "rejected" or "rolled_back" can be re-promoted by calling this endpoint with any valid UUID as `approval_id`. The governance gate at the API layer only checks that an `approval_id` exists (non-null Pydantic UUID), not that it corresponds to a real `Approval` record or that the proposal is in an appropriate lifecycle state.

Confidence: **confirmed** — no status guard in the route; any non-None UUID satisfies the Pydantic schema.

## Governance gate: fail-closed design

All three service-layer promotion methods raise `ValueError("Approval required: approval_id must not be None")` when `approval_id is None`. The API layer adds a structural layer: `PromoteRequest.approval_id` is typed `uuid.UUID` (non-optional), so Pydantic validation rejects null/missing values before the route body runs. There is no alternative code path that bypasses the check, no default parameter, and no conditional logic that could skip validation. The gap is at the lifecycle level: the route doesn't verify `approval_id` points to a real `Approval` record or that the proposal is in an approvable state.

## Test coverage gaps

179 test methods across 5 files cover all service-layer classes using direct instantiation with in-memory state (no DB fixtures). This thoroughly validates pure logic and governance gates but leaves untested:

- SQL query construction in API routes (filter application, ordering, pagination)
- The RAG pipeline's `search()` method which calls `db.exec()` directly
- API-level request validation and model serialization round-trips
- Foreign key constraint enforcement
