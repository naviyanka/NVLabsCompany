# Opt-in JSON persistence, restricted CORS, health probes, structured logging, and in-process metrics

Adds operational infrastructure to NEXUS without new external dependencies. Three subsystems gain opt-in file persistence via atomic writes (ControlRegistry, PhaseMachine, LayeredMemoryStore L2/L3). CORS moves from `allow_origins=["*"]` to a configurable origin list. Health probes gain DB connectivity checks. A new structured logging layer provides JSON output with per-request correlation IDs, and an in-process metrics system exposes a Prometheus-compatible `/metrics` endpoint.

Watch for: The in-flight request "gauge" is modeled as a Counter with negative increments, which violates Prometheus counter semantics and will confuse scrapers (confirmed). The `cors_origins` setting has an empty `env_prefix`, meaning the env var is `CORS_ORIGINS` not `NEXUS_CORS_ORIGINS` — this is consistent with the existing config pattern but could surprise operators expecting a namespace (confirmed, pre-existing pattern). Health probes import the database `engine` at module level, coupling the health router to the real DB engine at import time rather than at request time (confirmed).

**Verdict**: APPROVED

## High-level view

Persistence follows a consistent pattern across all three modules: optional `persist_path` parameter, atomic write via `tempfile.mkstemp` + `os.replace`, load-on-init if the file exists. The pattern is simple and correct for single-process deployments but offers no concurrency protection if two processes share a path.

CORS restriction moves `allow_origins` from wildcard to a comma-separated settings string. The health router adds three endpoints (`/health/live`, `/health/ready`, `/health`) with the readiness probe gated on a live DB query. The comprehensive `/health` endpoint always returns 200 — it reports degraded status in the body rather than via HTTP status code, which matches common Kubernetes patterns.

Structured logging and telemetry are two new stdlib-only modules. The RequestIDMiddleware propagates `X-Request-ID` via a context var that the JSON formatter reads. The telemetry module implements Counter and Histogram with thread-safe locks and a MetricsMiddleware that instruments every HTTP request. The in-flight counter abuses the Counter type as a gauge by decrementing — Prometheus clients model this as a separate Gauge type for good reason.

<details>
<summary>Issues (4)</summary>

1. **In-flight counter is semantically a gauge** — `http_requests_in_flight` uses `Counter` with `inc(amount=-1.0)` to decrement. Prometheus scrapers expect counters to be monotonically increasing. Use a separate `Gauge` class (even a trivial wrapper around an atomic int) or at minimum rename the metric type annotation from `counter` to `gauge` in the render output.
2. **Health router imports engine at module level** — `from nexus.database import engine` in `health.py` binds the module to whatever engine exists at import time. If the engine is recreated (e.g., during testing or hot-reload), the health probes will use the stale reference. Consider using a dependency or lazy import.
3. **Persistence has no file locking** — The atomic-write pattern prevents corruption from a single process, but two processes with the same `persist_path` can race between the `json.load` in `_load()` and the `os.replace` in `_persist()`, silently losing writes. If multi-process deployment is planned, this needs advisory locking or a note in the docs.
4. **`_start_time` in health module is module-load time, not app-start time** — `_start_time = time.time()` at module scope captures import time, which may differ from actual app readiness (lifespan completion). In practice the difference is small but becomes visible in pre-fork servers.

## Persistence concurrency gap

All three modules use `tempfile.mkstemp` + `os.replace` for atomic single-process writes. There's no advisory lock (`fcntl.flock` or equivalent) between `_load()` and `_persist()`. A second process sharing the same `persist_path` can read stale state, mutate in memory, and silently overwrite changes from the first process. For the stated use case (opt-in, single-process) this is acceptable but should be documented as a constraint. *Confidence: confirmed* — no locking mechanism exists in the code.

## In-flight counter abusing Counter semantics

`http_requests_in_flight` is declared as a `Counter` but used as a gauge:

```python
http_requests_in_flight.inc(labels={"state": "active"})   # +1 on request start
http_requests_in_flight.inc(amount=-1.0, labels={"state": "active"})  # -1 on finish
```

The `render_metrics()` function emits this with `# TYPE http_requests_in_flight counter`. A Prometheus scraper seeing a counter decrease between scrapes will treat it as a counter reset, producing wrong `rate()` calculations. The fix is either a dedicated Gauge class or changing the TYPE annotation to `gauge` in the renderer. *Confidence: confirmed* — the render output explicitly uses `"# TYPE {name} counter"` for all Counter instances.

## Health probe coupling to module-level engine

```python
from nexus.database import engine
```

This captures the engine reference at import time. If the engine is swapped (testing, dynamic reconfiguration), health probes continue using the original object. The test suite works around this with `patch("nexus.api.routes.health.engine", ...)`, confirming the coupling requires mocking. *Confidence: confirmed.*

## Test coverage gaps

59 new tests cover persistence round-trips, health probes, and logging/telemetry. Not tested: concurrent writes to the same persist file. Not tested: MetricsMiddleware behavior when the inner app raises before `http.response.start` is sent (the status_code defaults to "500" which is reasonable, but there's no explicit test confirming this path). Not tested: the `_start_time` drift between module load and lifespan completion.
