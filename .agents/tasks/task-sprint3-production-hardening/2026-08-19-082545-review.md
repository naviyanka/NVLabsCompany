# Sprint 3: Production Hardening — v2 review after fixes

This sprint adds six subsystems to NEXUS: tool governance (policy engine, profile resolution, catalog registry), tool invocation auditing with recursive argument scrubbing, a goal-gated autonomous loop with safety valves, a decision queue/triage system, a replay engine for timeline reconstruction, and git worktree isolation for parallel agent execution. Six of the seven issues from the v1 review have been fixed; the seventh (Alembic migration) was intentionally deferred per deployment process. All 1081 tests pass.

Watch for: ProfileResolver specificity-first semantics remain undocumented — agent-level bindings always win regardless of numeric priority (likely, informational only). No remaining blocking concerns.

**Verdict**: APPROVED

## High-level view

The argument scrubbing now recursively traverses nested dicts and lists via a `_scrub_value` helper, closing the compliance gap where deeply nested credentials could reach the audit store unmasked.

The GoalLoop wraps `execute_fn` in try/except and returns a `GoalResult` with `stopped_reason="execution_error"`, preserving any prior iteration's output. This brings execution errors in line with the existing graceful handling of judge exceptions.

`decide_item` now stores the decision string in a `decision_outcome` field on `DecisionQueueItem`, making the triage system's primary output accessible for queries and reporting.

`ToolExecutor.execute()` accepts a `tool_name` parameter that flows through to `_record_invocation`, ensuring audit records carry the human-readable tool identifier instead of an empty string.

All `datetime.utcnow()` calls in the new `tool.py` models and `tool_invocation.py` have been replaced with `datetime.now(timezone.utc)`, eliminating the deprecation warnings for this sprint's code.

`create_worktree` now wraps the worktree creation step in try/except and calls `git branch -D` to clean up the orphaned branch before re-raising, preventing branch pollution on partial failure.

## ProfileResolver hierarchy vs priority ambiguity

The `ProfileResolver.resolve()` method iterates target types in specificity order (agent, department, company) as its outer loop, then checks bindings in numeric-priority order within each level. This means a priority-999 agent binding always wins over a priority-0 company binding. The docstring says "checks agent → department → company bindings in priority order" — which is technically correct but misleading, since "priority order" could be read as numeric priority being the primary sort key.

This is a documentation clarity issue, not a behavioral bug. The hierarchical override model (most specific scope wins) is a reasonable design for profile resolution. The risk is that a future developer adds a company-wide emergency deny-all binding at priority 0, expecting it to override agent-level bindings, and is surprised when it doesn't.
