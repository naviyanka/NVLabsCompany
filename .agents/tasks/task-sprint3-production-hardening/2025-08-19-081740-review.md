# Sprint 3: Production Hardening + Advanced Features

This sprint adds six capabilities to NEXUS: enterprise tool governance (policy engine, profile resolution, catalog registry), tool invocation auditing with argument scrubbing, a goal-gated autonomous loop with safety valves, a decision queue/triage system, a replay engine for task timeline reconstruction, and git worktree isolation for parallel agent execution. The implementation is entirely additive — no existing behavior is modified — and follows the project's established patterns (SQLModel tables, in-memory service classes, dataclasses for DTOs). All 170 new tests pass alongside the existing suite (1070 total).

Watch for: `_scrub_arguments` only scrubs top-level keys so nested secrets pass through unmasked (confirmed). The `GoalLoop` has no safety valve for `execute_fn` raising — an exception propagates and crashes the loop with no `GoalResult` (confirmed). `decide_item` accepts a `decision` parameter but discards it, so the actual decision outcome is lost (confirmed). `ToolInvocation.tool_name` is always stored as empty string by the executor (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The tool governance layer introduces five new SQLModel tables and an in-memory policy engine that evaluates allow/deny rules in priority order with fnmatch-based tool name patterns and time-of-day gating. The `ProfileResolver` prioritizes specificity (agent > department > company) over numeric priority, meaning a priority-0 company binding never overrides a priority-99 agent binding — the docstring describes this as "priority order" without clarifying the specificity-first semantics.

The audit subsystem wraps the existing `ToolExecutor` with a structured `ToolInvocation` record for every execution path (success, error, timeout, denied, rate-limited). Argument scrubbing is shallow — only top-level dictionary keys are inspected — so credentials nested inside complex argument objects are stored in plaintext.

The goal-gated loop is a straightforward iterate-then-judge design with three circuit breakers (max iterations, budget, parse failures). It does not handle `execute_fn` exceptions, which means an LLM API failure or network error kills the loop entirely rather than recording a graceful stopped_reason.

The decision queue is a pure in-memory triage system layered on top of the existing `DecisionQueue` SQLModel table. It manages lifecycle (pending → snoozed → decided → archived) but discards the actual decision content — the `decision` string parameter in `decide_item` is accepted but never stored.

The worktree manager shells out to git via async subprocess with conflict detection and abort-on-failure semantics, but `create_worktree` has no rollback if the worktree creation step fails after the branch is already created.

## Argument scrubbing misses nested structures

The `_scrub_arguments` function in `executor.py` iterates top-level keys only:

```python
def _scrub_arguments(arguments: dict[str, Any]) -> dict[str, Any]:
    scrubbed: dict[str, Any] = {}
    for k, v in arguments.items():
        if any(s in k.lower() for s in _SENSITIVE_KEYS):
            scrubbed[k] = "***"
        else:
            scrubbed[k] = v
    return scrubbed
```

A tool invoked with `{"credentials": {"api_key": "sk-live-xxx", "token": "bearer-yyy"}}` stores the nested secrets verbatim in `arguments_scrubbed` because the outer key `"credentials"` doesn't match any sensitive substring. This is an audit compliance gap — the scrubbing provides a false sense of security for any tool that passes structured arguments.

## GoalLoop has no execute_fn exception handling

The loop awaits `execute_fn()` without a try/except:

```python
output, cost_cents = await execute_fn()
total_cost += cost_cents
final_output = output
```

If `execute_fn` raises (LLM timeout, network error, tool crash), the entire `run()` method propagates the exception with no `GoalResult` returned. The caller gets an unhandled exception instead of a structured result with `stopped_reason="execution_error"`. The judge exception path is handled carefully with the consecutive-failure counter, but the execution path has no analogous protection. This asymmetry means the loop is fail-crash for execution errors but fail-graceful for judge errors.

## Decision content silently discarded

`decide_item` accepts a `decision: str` parameter documented as "stored as a status transition marker" but the method only sets `item.status = "decided"` and never stores the string. In a triage system, the actual decision ("approved", "rejected", "deferred to legal") is the primary output. The current implementation lets callers believe they're recording a decision when they're only recording that *some* decision was made.

## ToolInvocation.tool_name hardcoded empty

In `_record_invocation`:

```python
invocation = ToolInvocation(
    ...
    tool_name="",
    ...
)
```

The `execute` method receives `tool_id` but not `tool_name`. Since `tool_name` is a non-nullable string field on the ToolInvocation model, it's populated with an empty string. Audit queries filtering by tool_name will never match. Either accept `tool_name` as a parameter to `execute()` or resolve it from the registry.

## ProfileResolver specificity-first semantics

The resolver iterates `(agent, department, company)` targets as its outer loop and bindings as its inner loop. This means any agent-level binding (even one with priority=999) is selected before any department-level binding (even one with priority=0). The docstring says "checks agent → department → company bindings in priority order" which conflates two dimensions (specificity and numeric priority). If the intent is purely hierarchical override (agent always wins), clarify the docstring. If numeric priority should be the global tiebreaker, the iteration order needs to be inverted (bindings outer, targets inner).

## Missing Alembic migration for six new tables

`tool_connections`, `tool_catalog_entries`, `tool_profiles`, `tool_profile_bindings`, `tool_policies`, and `tool_invocations` exist in SQLModel metadata (validated by `test_alembic_migration.py` checking for 54 tables) but there is no `alembic/versions/` file that creates them. The test asserts metadata correctness but doesn't assert that an upgrade path exists from the previous migration head.

## Worktree branch orphaned on partial failure

`create_worktree` runs two git commands sequentially:

```python
await self._run_git(repo_path, "branch", branch)
await self._run_git(repo_path, "worktree", "add", worktree_dir, branch)
```

If the second command fails (directory not writable, disk full, path conflict), the branch created by the first command persists with no worktree attached. A subsequent `create_worktree` call for the same agent will fail because the branch already exists. The fix is to catch the RuntimeError from the worktree step and delete the orphaned branch.
