# 3D Isometric Office Floor Plan — v2 Review

The five blocking issues from v1 have all been addressed: the Office page is now lazy-loaded (954KB separate chunk), the GPU render loop pauses when the tab is hidden via `usePageVisibility` + `frameloop="demand"`, a full `OfficeMobileFallback` component handles screens under 768px, "View Full Profile" navigates to `/agents/:id`, and the fragile `(e as unknown as ...)` casts were replaced with proper `ThreeEvent<MouseEvent>` typing. The page still operates on static mock data by design — this is a demo/prototype, and the data layer split is a conscious scope boundary.

Watch for: The `mouseButtons` mapping in `CameraControls` inverts left-click and right-click, making the default drag gesture a pan (right mouse) rather than orbit, which contradicts the "Drag to pan" hint in StatsBar (confirmed). The `StatsBar` and `AgentsAtGlance` components are still rendered in the desktop layout even though they overlap the canvas at extreme aspect ratios (likely). Two stale `useMemo` patterns remain in animation components — benign now but a latent footgun if data becomes dynamic (confirmed).

**Verdict**: APPROVED

## High-level view

The camera control configuration assigns `mouseButtons.LEFT = 2` (which maps to `THREE.MOUSE.PAN`) and `mouseButtons.RIGHT = 0` (`THREE.MOUSE.ROTATE`). This means left-click-drag pans and right-click-drag rotates. The `StatsBar` hint text says "Drag to pan · Scroll to zoom · Click agent to inspect," which is technically accurate for left-drag, but "right-click to orbit" is undiscoverable and conflicts with the browser context menu on some platforms.

The two remaining `useMemo(..., [])` patterns in `DelegationAnimation` and `ReportAnimation` will silently produce stale filtered agent lists if the data source ever changes from a static import to props/context. This was flagged in v1 as informational context — it remains accurate but is not blocking given the deliberate static-data scope.

## Camera controls interaction model

`CameraControls` passes a `mouseButtons` object that remaps the standard OrbitControls behavior:

```tsx
mouseButtons={{
  LEFT: 2,   // THREE.MOUSE.PAN
  MIDDLE: 1, // THREE.MOUSE.DOLLY
  RIGHT: 0,  // THREE.MOUSE.ROTATE
}}
```

The intent is reserving left-click for agent selection (since OrbitControls' default left-drag would conflict with clicking agents). Assigning orbit to right-click means the browser's native context menu will fire on `mouseup` after every orbit gesture on platforms that don't suppress it. R3F's Canvas doesn't automatically call `preventDefault()` on right-click, so users on Windows/Linux will see a context menu flash after every orbit attempt.

A cleaner pattern would be to disable orbit entirely (this is an isometric view with constrained angles — orbit adds little value) or use middle-click for orbit and leave right-click unmapped. The polar/azimuth angle limits already constrain rotation to a narrow range (±45° azimuth, 30°–60° polar), suggesting orbit is more of a "tilt adjustment" than a primary interaction.

## Overlay stacking at intermediate viewport widths

The mobile fallback triggers at `max-width: 767px`, so any viewport ≥768px gets the full 3D scene with all three overlay layers:

- `StatsBar`: absolute top, full width, `z-10`
- `AgentsAtGlance`: absolute bottom, full width, `z-10`
- `AgentDetailSidebar`: absolute top-14 right-0 bottom-0, `w-80`, `z-20`

On a 768px-wide viewport with the sidebar open, the sidebar consumes 320px (41% of width), and the bottom cards still render full-width behind it. The cards at the right edge are clipped by the sidebar's higher z-index but remain interactive via pointer events, creating a dead zone where clicks appear to do nothing. The StatsBar's stat items (`gap-5` flex with 5 items) will also wrap awkwardly between 768px and ~900px, where there isn't enough room for all five inline.
