# Phase 2 Reliability: Redis state, pluggable Hive, Docker sandbox, L1 persistence, LLM circuit breaker, degradation endpoint

Six reliability primitives added across governance, communication, evolution, memory, adapters, and API layers. The approach is consistent: define a Protocol, provide a file/local fallback implementation and a Redis/Docker enhanced implementation, gate at runtime, and fall back gracefully. A new `/system/degradation` endpoint ties them together by probing each subsystem's availability and returning structured status.

Watch for: The RedisHiveBackend's sync-wrapping-async pattern (confirmed) silently drops messages when called inside a running event loop. The degradation endpoint's Redis health check creates connection churn on every request (confirmed). The `FileStateBackend.list_keys` key-reconstruction logic is lossy and will collide on keys containing both `/` and `__` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The state backend introduces a `StateBackend` Protocol with Redis and file implementations, connected by a factory that ping-tests Redis and falls back. The Redis implementation goes permanently unavailable after a single failure — no recovery mechanism, no periodic re-probe — which means transient network blips permanently disable the backend until process restart.

The HiveManager is made pluggable by accepting an optional `HiveBackend` parameter while retaining its built-in file logic as the default path. A `RedisHiveBackend` is provided, but its sync-wrapping-async approach (`asyncio.ensure_future` inside running loops) silently discards messages without delivery confirmation, and `get_inbox` returns `[]` unconditionally in async contexts, making it non-functional in FastAPI.

Docker sandbox wraps `docker run` with memory/CPU limits, `--network=none`, and `--read-only`. The `--read-only` flag will break most Python scripts that need `/tmp`; a `--tmpfs /tmp` mount is missing. The fallback path returns a synthetic result without executing user code.

L1 persistence extends the layered memory system by writing session summaries to a separate `_l1.json` file using the same atomic write pattern as L2/L3.

The LLM circuit breaker implements the closed → open → half-open state machine. All failures — including programming errors like `TypeError` — trip the breaker and return a fallback response rather than propagating, which conflates transient infra failures with permanent bugs.

The degradation endpoint checks Redis, Docker, LLM, embeddings, and memory import availability. It creates a fresh Redis connection pool per request rather than reusing an application-scoped client.

4. **RedisStateBackend no recovery path** (confirmed) — After any exception sets `_available = False`, no operation will succeed until process restart. Add a periodic health-check or attempt reconnection after a cooldown.
5. **Degradation endpoint Redis connection churn** (confirmed) — `_check_redis` creates a new connection pool on every request, pings, then closes it. Under load this churns Redis connections. Use an application-scoped client or reuse the state backend's connection.
6. **Degradation overall_status dead branch** (confirmed) — The trailing `else: overall = "degraded"` is unreachable because the preceding conditions exhaustively partition the states. Remove it or handle the "all degraded, none unavailable" case explicitly.
7. **Docker sandbox `--read-only` without tmpfs** (confirmed) — The container is launched with `--read-only` but no `--tmpfs /tmp`. Most Python scripts write to temp directories and will fail with `OSError`.
8. **LLM circuit breaker catches all exceptions** (likely) — `TypeError`, `AttributeError`, and other programming errors trip the breaker and are silently swallowed instead of propagating. Distinguish transient failures (timeout, connection error) from permanent errors.
9. **Docker sandbox fallback returns synthetic result** (confirmed) — The fallback lambda returns a description string rather than executing user code. If Docker detection fails post-init, users get fake results without indication they're synthetic.

## RedisHiveBackend sync-async impedance mismatch

The `HiveBackend` Protocol defines all methods as synchronous (`def`, not `async def`), which forces `RedisHiveBackend` to wrap every async Redis call in an event-loop dance:

```python
def send_message(self, msg: HiveMessage) -> None:
    try:
        loop = asyncio.get_event_loop()
        if loop.is_running():
            asyncio.ensure_future(self._async_send_message(msg))
        else:
            loop.run_until_complete(self._async_send_message(msg))
    except RuntimeError:
        asyncio.run(self._async_send_message(msg))
```

When the loop is running (the normal case in a FastAPI application), `ensure_future` schedules the coroutine but the caller gets no confirmation it succeeded. If `_async_send_message` raises, the exception is swallowed into the event loop's exception handler. Messages may be silently lost.

The `get_inbox` case is worse — it returns `[]` immediately when the loop is running because there's no way to synchronously await the result. The Redis inbox is effectively non-functional when called from async code.

The fix is either to make `HiveBackend` Protocol methods `async def` (breaking change to the interface but correct), or to provide a separate `AsyncHiveBackend` protocol that `HiveManager` uses when running in async context.

## Redis state: single-failure latch

`RedisStateBackend` sets `self._available = False` on any exception in `get`, `set`, `delete`, or `list_keys`. Once latched, every subsequent operation short-circuits to a no-op return value. The `health_check()` method exists and _does_ reset `_available = True` on success, but nothing calls it after initialization.

In a long-running service, a single Redis timeout during a network partition permanently disables the state backend. The `FileStateBackend` fallback isn't activated either — it's a one-time factory decision, not a runtime failover.

## FileStateBackend key encoding collision

```python
def _key_path(self, key: str) -> Path:
    safe_key = key.replace("/", "__").replace(":", "_")
    return self._dir / f"{safe_key}.json"
```

```python
key_name = path.stem.replace("__", "/").replace("_", ":")
```

Key `"a__b"` maps to file `a__b.json`. Key `"a/b"` also maps to file `a__b.json`. When listing keys, `a__b.json` is decoded as `"a/b"`, so the original `"a__b"` key is lost. Similarly, `"a_b"` and `"a:b"` collide on the file `a_b.json`. Any key containing underscores or double-underscores as literal characters will be mishandled.

## Docker sandbox: `--read-only` without tmpfs

The Docker container is launched with `--read-only`, which prevents writes to the container filesystem. Many Python scripts need `/tmp` or write intermediate files. Without a writable tmpfs mount (`--tmpfs /tmp`), real Python code execution will fail with `OSError` whenever it tries to write anywhere.

## LLM circuit breaker: all-exception catch

```python
except Exception as exc:
    logger.warning("LLM call failed: %s", exc)
    self._on_failure()
    return self._config.fallback_response
```

Programming errors in the wrapped callable (e.g., `TypeError` from wrong arguments, `AttributeError` from a misconfigured client) also trip the breaker and are silently swallowed. Transient failures (timeout, connection error, 5xx) should count toward the threshold; permanent errors (bad config, auth failure) should propagate immediately.

## Test coverage gaps

Not tested: RedisHiveBackend behavior inside a running async loop (the `ensure_future` path), FileStateBackend key collisions with special characters, Docker sandbox with `--read-only` failing on write, LLM circuit breaker with non-transient exceptions (TypeError, ValueError).
