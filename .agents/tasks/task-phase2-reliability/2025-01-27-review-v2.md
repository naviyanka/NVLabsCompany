# Phase 2 Reliability: Redis state, pluggable Hive, Docker sandbox, L1 persistence, LLM circuit breaker, degradation endpoint

Six reliability primitives added across governance, communication, evolution, memory, adapters, and API layers. The v1 review's 9 issues have all been addressed: the HiveBackend protocol is now fully async, the FileStateBackend uses percent-encoding for bijective keys, RedisStateBackend has a recovery cooldown, the Docker sandbox includes `--tmpfs /tmp`, the circuit breaker distinguishes transient from permanent errors, the degradation endpoint uses a Redis singleton, and the fallback result includes an `is_fallback` indicator.

Watch for: `RuntimeError` in TRANSIENT_EXCEPTIONS is overly broad — it covers every `RuntimeError` including unrelated programming bugs like "dictionary changed size during iteration" (likely). The `RedisHiveBackend` still latches permanently unavailable on a single failure with no recovery path, unlike its `RedisStateBackend` sibling that now has cooldown-based recovery (confirmed). The HiveManager `_run_async` spawns a thread pool per sync call, which has latency and resource implications under load (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The `RedisStateBackend` now has cooldown-based recovery, but `RedisHiveBackend` was not given the same treatment — a single failure permanently disables it until process restart.

The `HiveBackend` protocol is now all-async, eliminating the fire-and-forget problem. The sync bridge in `HiveManager._run_async` spawns a fresh `ThreadPoolExecutor(max_workers=1)` per call when inside a running event loop, churning threads proportional to call frequency rather than reusing a single executor.

The LLM circuit breaker correctly separates transient from permanent exceptions, but `RuntimeError` in the transient list is too broad. `OSError` and `ConnectionError` already cover network-level failures; `RuntimeError` additionally catches event loop misuse, state corruption, and other programming bugs that should propagate.

1. **RuntimeError in TRANSIENT_EXCEPTIONS** (likely) — `RuntimeError` is a common base for non-infrastructure errors (e.g., "cannot reuse already awaited coroutine", "dictionary changed size during iteration"). Including it means those programming bugs silently trip the breaker and return fallback instead of propagating. Remove it or narrow to specific subclasses.
2. **RedisHiveBackend no recovery path** (confirmed) — Unlike `RedisStateBackend` which now has cooldown-based recovery, `RedisHiveBackend` permanently latches `_available = False` on any single failure. Add the same cooldown-probe pattern used in `RedisStateBackend`.
3. **HiveManager _run_async thread pool per call** (confirmed) — Each sync method invocation when inside a running event loop creates a new `ThreadPoolExecutor(max_workers=1)`. Under moderate call frequency this churns threads. Use an instance-level or module-level executor.
4. **HiveManager _run_async 10s hard timeout** (confirmed) — The `.result(timeout=10)` hard-codes a 10-second deadline for every backend operation. A slow Redis under GC pressure or a scan over a large registry could hit this and raise `TimeoutError` to the caller, which may not expect it from a sync `get_registry()` call. Make configurable or document the failure mode.

## RuntimeError classified as transient in LLM circuit breaker

The `TRANSIENT_EXCEPTIONS` tuple includes `RuntimeError`:

```python
TRANSIENT_EXCEPTIONS: tuple[type[BaseException], ...] = (
    asyncio.TimeoutError,
    TimeoutError,
    ConnectionError,
    ConnectionRefusedError,
    ConnectionResetError,
    ConnectionAbortedError,
    OSError,
    IOError,
    RuntimeError,
)
```

`RuntimeError` is Python's general-purpose exception for "something is wrong" — it's raised for event loop misuse (`"This event loop is already running"`), coroutine reuse, generator state violations, and myriad library-level bugs. If an LLM adapter raises `RuntimeError("model not initialized")` due to a configuration error, the breaker swallows it and returns fallback, never surfacing the root cause.

The network-level failures `RuntimeError` might have been intended to catch (e.g., aiohttp internals) are already covered by `ConnectionError` and `OSError`. Removing `RuntimeError` from the list tightens the classification without losing infrastructure-failure coverage. `ConnectionRefusedError`, `ConnectionResetError`, and `ConnectionAbortedError` are also redundant as subclasses of `ConnectionError` — harmless but noisy.

## RedisHiveBackend lacks recovery cooldown

`RedisStateBackend` was fixed in this round with `_check_recovery()` — after a failure, it waits `recovery_cooldown_seconds` (default 30s) then probes with PING. `RedisHiveBackend` uses the same `_available` flag pattern but sets it to `False` permanently:

```python
except Exception as exc:
    logger.warning("Redis hive send failed: %s", exc)
    self._available = False
```

No method ever resets it. A transient Redis blip permanently disables the Hive backend for the remainder of the process lifetime. The same cooldown-probe pattern from `RedisStateBackend` should be applied here.

## HiveManager thread-per-call bridge

When a sync method is called inside a running event loop, `_run_async` creates a fresh executor:

```python
import concurrent.futures
with concurrent.futures.ThreadPoolExecutor(max_workers=1) as pool:
    return pool.submit(asyncio.run, coro).result(timeout=10)
```

The `with` block creates and tears down a thread pool on every call. An instance-level `ThreadPoolExecutor` eliminates this overhead.

The hard-coded 10-second timeout will raise `concurrent.futures.TimeoutError` if the backend operation is slow. Since the sync methods have no documented timeout contract, callers aren't prepared to handle this. Either expose it as a configurable parameter or catch and convert to a logged warning with graceful degradation.
